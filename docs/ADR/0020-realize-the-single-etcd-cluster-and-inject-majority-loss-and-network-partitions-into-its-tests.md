# 0020: 単一 etcd クラスタを 3 メンバーの試験クラスタ・テナントビュー・相乗り計測で実現し、過半数喪失とネットワーク分断を試験に注入する

## コンテキスト

[[0005]] は、G0〜G1 の強整合ストアを 3 台構成の単一 etcd v3.6 クラスタとし、全テナントのデータを `/t/<tenant>/` の下に置き、G0 ではホット領域も同じクラスタに載せる、と決めた。[[0019]] はその実現方式（3 メンバーの試験クラスタ、メンバー障害の注入、テナントビュー、相乗り計測、開発用クラスタ、アダプタの定足数読み取り）を決め、実装済みである。

[[0019]] は、過半数の喪失とネットワーク分断を「注入しない」と決め、[[0015]] の決定論的シミュレーションを決めるときに扱うとした。この範囲を変える理由は 2 つある。

- 3 メンバーにしただけで、`etcdstore` が契約を破る経路が 3 つ見つかった。どれも、遅れたフォロワーが自分の状態だけで答える経路だった。少数派に取り残されたメンバーは、遅れたフォロワーよりも長く、古い状態のまま応答し続ける。同じ種類の誤りがまだ残っていないかを、実物の etcd で確かめる手段が無い。
- [[0015]] のシミュレーションは、単一のシードで決まるイベントキューの上で走り、実ネットワークと実時間を使わない。シミュレータはまだ選ばれておらず、etcd をそこに載せられるかは確かめていない。それまでのあいだ、etcd とそのクライアントの挙動（リーダーを失ったメンバーの応答、watch の打ち切り、エンドポイントの切り替え）は、実物の etcd に障害を入れなければ検査されない。

本 ADR は [[0019]] を置き換える。[[0019]] の決定 1〜6 は引き継ぎ、決定 2 のうち注入しないとした範囲を決定 7〜9 で変える。DocDag の辺は置き換えと依存の 2 種類であり、一部だけを改める辺は無いので、全体を書き直す。

[[0006]] は `proposed` である。本 ADR が使うのは `/t/<tenant>/` という接頭辞だけであり、その下の配置（`o/`・`own/`・`ref/`・`bind/`）と `/sys/`・`/x/` は [[0006]] の範囲に残す。

## 決定

1. **試験の既定を 3 メンバーにする。** `etcdtest.Start` は、ループバック上に 3 メンバーの etcd を静的ブートストラップで起動する。クライアントには 3 つのエンドポイントをすべて渡す。契約テスト・線形化可能性検査・DRT はすべてこのクラスタにかけ、メンバー 1 台の構成は残さない。試験は 3 メンバーすべてが 3.6 系を報告することを確かめる。試験用のメンバーは `--unsafe-no-fsync` で起動する。
   - ポートは、エフェメラル範囲より下の番号のブロックを、ファイルロックでクラスタごとに確保する。
2. **メンバー障害を注入する。** 線形化可能性検査の最中に、メンバーを 1 台ずつ停止して再起動する。対象にはリーダーを含める。
   - エラーで返った `Txn` は結果不明として扱う。履歴には、最後まで戻らなかった操作として記録し、適用された場合と適用されなかった場合の両方を許す。
   - エラーで返った読み取りは状態を変えないので、履歴に入れない。
   - watch は障害で終わってよい。試験は、最後に受け取ったリビジョンの次から開き直し、つなげた列に欠落・重複・順序の入れ替わりが無いことを確かめる。1 台の停止では watch は終わらないので、試験は自分で watch を終わらせて開き直す。
3. **テナントビューを置く。** `core/store/tenant` は、`store.Store` を `/t/<tenant>/` の下に閉じ込めるビューを提供する。
   - テナント名は RFC 1123 のラベルとする。小文字の英数字と `-` だけを使い、先頭と末尾は英数字、長さは 1〜63 バイトである。これ以外の名前ではビューを作れない。
   - ビューの型は `Get`・`Range`・`Txn`・`Watch`・`CurrentRev` だけを持つ。`Compact` は持たない。コンパクションはクラスタ全体の `store.Store` を持つ側だけが行う。
   - ビューはキーの接頭辞だけを付け外しする。リビジョンは変えない。したがってテナントが見るリビジョンはクラスタ全体のリビジョンであり、他テナントの書き込みでも進む。
   - ビューは権限の境界ではない。クラスタ全体の `store.Store` を持つコードは、どのテナントのキーにも届く。etcd の認証と RBAC は本 ADR では設定しない。
4. **ホット領域に専用の型を作らない。** G0 のホット領域は同じ `store.Store` を使う。専用のインタフェースやキー接頭辞は、G1 で別層への分離を検証するときに入れる。代わりに、相乗りの影響を測る計測を `storetest` に置く。計測は、強整合側の書き込みと watch の遅延を、ホット側の高頻度書き込みが無いときと有るときで比べ、分位点を報告する。合否の閾値は置かない。
5. **開発用クラスタを宣言する。** `config/dev.lkal` に、etcd の版と 3 メンバーの URL を宣言し、`config/dev.schema.lkal`（LKAL v0.2 スキーマ）で構造を固定する。`cmd/dev-etcd` は `lkal.Parse` と埋め込みスキーマ（`github.com/Kaikei-e/LKAL/schema`）でその宣言を検証・読込し、宣言と同じ版の etcd を 3 メンバーでローカルに起動する（[[0027]]。当初の `lkal json -plain` 外部コマンド呼び出しを置き換えた）。版が宣言と違えば起動しない。データの既定の置き場所はリポジトリの外にする。
6. **アダプタは、etcd がメンバー自身の状態だけで答える経路を定足数読み取りに通す。** どれも、遅れているフォロワーが応答したときにだけ現れる。
   - 書き込みを持たない `Txn`（比較だけの `Txn`）には、線形化可能な読み取りを 1 つ、成功側と失敗側の両方に添える。
   - `fromRev` が 0 の `Watch` は、先に `CurrentRev` を読む。etcd の watch は開始リビジョン 0 のまま開き、読んだリビジョン以下の変更はアダプタが捨てる。
   - `fromRev` が正の `Watch` は、先にそのリビジョンを線形化可能に読む。コンパクション済みなら、`ErrCompacted` で終わった watch を返す。未来のリビジョンは許す。
   - `Watch` の中の読み取りが呼び出し側のコンテキストの終了で失敗したときは、エラーを返さず、そのコンテキストの誤りで終わった watch を返す。
   - 回帰テストは、フォロワーのプロセスを一時停止して遅らせ、そのフォロワーだけに接続したクライアントで問い合わせる。
7. **過半数の喪失を注入する。** 3 メンバーのうち 2 台を同時に止める。止め方は、停止して再起動する方法と、一時停止して再開する方法の 2 つを使う。
   - 過半数の喪失を確かめてから回復を始めるまでのあいだに応答した `Txn` と線形化可能な読み取りは、成功であってはならない。喪失は、操作が 1 つ失敗することで確かめる。
   - 期限が回復をまたぐ操作は、回復のあとに成功しうる。その正しさは線形化可能性検査に委ねる。
   - 過半数が戻れば、試験は何も操作せずにクラスタが応答を再開することを確かめる。
   - 喪失をまたいだ履歴全体に、線形化可能性検査をかける。
8. **ネットワーク分断を、送信元を見分けるピアプロキシで注入する。** `etcdtest` は、メンバーごとに HTTP のプロキシを 1 つ置く。メンバーが他のメンバーに広告するピア URL はプロキシのものにし、プロキシは受けた要求をそのメンバーの実際のピア URL に渡す。
   - プロキシは、要求ごとに `X-Server-From` ヘッダから送信元のメンバーを読む。etcd は Raft のメッセージを運ぶ 3 つの経路すべてにこのヘッダを付ける。
   - 分断は、メンバーの組を単位に切る。組が切れているあいだ、プロキシはその組の要求と、すでに流れているストリームを、転送も切断もせずに止める。
   - 分断を解くとき、止めていた接続を閉じる。etcd は自分から張った接続に読み書きのタイムアウトをかけないので、閉じなければ張り直しが起きず、回復しない。
   - Raft のメッセージを運ぶ経路（`/raft`・`/raft/snapshot`・`/raft/stream/`）への要求がこのヘッダを持たなければ、プロキシは接続を切る。それ以外の経路の、ヘッダを持たない要求は通す。
   - 宛先のメンバーが止まっているとき、プロキシは応答を作らずに接続を切る。
   - 試験に見せる操作は、メンバー 1 台を他の 2 台から切り離すことと、分断を解くことの 2 つとする。多数派と少数派に分かれる分断は、3 メンバーではこの形だけである。
   - 切り離す対象には、フォロワーとリーダーの両方を使う。
   - プロキシが実際に分断していることを、試験で確かめる。切り離したフォロワーのリビジョン（そのメンバーだけに問い合わせる直列化可能読み取り）が、残りの 2 台への書き込みで進まないこと。リーダーを切り離すと、残りの 2 台が新しいリーダーを選ぶこと。分断を解くと、切り離したメンバーが残りの 2 台のリビジョンに追いつき、線形化可能な読み取りに答えること。
   - プロキシ単体の挙動（切れた組の新しい要求を渡さないこと、流れているストリームを止めること、分断中は相手に切断を見せないこと、解くときに閉じること、ヘッダの無い Raft の要求を切ること）は、etcd を使わない試験で確かめる。
   - 試験クラスタのピア通信は平文の HTTP とする。
9. **分断と過半数喪失のもとで、アダプタの契約を確かめる。**
   - 線形化可能性検査の障害注入に、決定 7 と 8 を加える。障害は 1 つずつ入れる。次の障害は、全メンバーが線形化可能な読み取りに答えるようになってから入れる。
   - 切り離したメンバーだけに接続したクライアントで、`atRev` が 0 の読み取り・`CurrentRev`・比較だけの `Txn`・`Watch` を呼ぶ。分断を解くまで、どれも成功してはならない。呼ぶのは、残りの 2 台への書き込みが確定したあととし、各呼び出しの期限は分断を解く前に切れるようにする。
   - 切り離したメンバーに開いてある watch は、誤りで終わる。試験は、終わるまでに届いたイベントが契約どおりであることと、多数派の側に開き直してつなげた列に欠落・重複・順序の入れ替わりが無いことを確かめる。
   - 1 組だけを切る分断、片方向だけの分断、遅延・損失・並べ替え、クライアントとメンバーのあいだの分断、時計のずれ、ディスク障害は注入しない。

## 根拠（調査結果・出典）

- **内部不変条件（[[0004]] の契約）**：`core/store/store.go` は、`atRev` が 0 の読み取り・`CurrentRev`・`Txn` を線形化可能と定める。`RequestProgress` は watch が追いつくまで要求を黙って捨ててよく、呼び出し側は十分なリビジョンの通知が届くまで再要求する。watch は、ストアの誤りで終わったとき `Err` でその誤りを返す。3 メンバーでも、分断のもとでも、契約の文面は変えずに検査できる。
- **3 メンバーの静的ブートストラップ**（ https://etcd.io/docs/v3.6/op-guide/clustering/ ）：各メンバーに `--name`、`--initial-advertise-peer-urls`、`--listen-peer-urls`、`--listen-client-urls`、`--advertise-client-urls`、`--initial-cluster-token`、`--initial-cluster`、`--initial-cluster-state new` を渡す。`--initial-cluster` と `--initial-cluster-token` は全メンバーで同じ値にする。同じ設定で複数の試験クラスタを作るときは、クラスタごとに別のトークンを与える。広告するピア URL と待ち受けるピア URL は別のフラグなので、あいだにプロキシを置ける。
- **メンバー障害時の挙動**（ https://etcd.io/docs/v3.6/op-guide/failures/ ）：3 メンバーのクラスタは 1 台の停止に耐える。リーダーが止まると、選挙タイムアウト程度のあいだ書き込みは処理されず、その間の書き込みは待たされるかタイムアウトする。旧リーダーに送られて未コミットの書き込みは失われることがあるが、コミット済みの書き込みは失われない（"no committed writes are ever lost"）。過半数を失うと書き込みを受け付けなくなり、過半数が戻れば自動で回復する。分断では多数派の側だけが応答し、少数派の側のリーダーは退く。
- **API の保証**（ https://etcd.io/docs/v3.6/learning/api_guarantees/ ）：KV 操作は耐久性と厳密な直列化可能性を持つ。直列化可能読み取りは、定足数に対して古いデータを返すことがある。タイムアウトやネットワーク障害のとき、クライアントは操作が完了したか分からないことがある。リーダー選挙のあいだ etcd は操作を中断することがあるが、未応答の要求に中断の応答は送らない。watch は順序どおり・重複なし・欠落なしで、最後に受け取ったリビジョンから再開できる。
- **結果不明の操作の扱い**（ https://github.com/jepsen-io/jepsen/blob/main/doc/tutorial/03-client.md ）：Jepsen は、起きなかったと分かる操作を `:fail`、分からない操作を `:info` とし、後者を「起きたかもしれないし起きなかったかもしれない」ものとして検査する。porcupine の `Operation` は呼び出しと応答の時刻で閉区間を表すだけで、結果不明の操作を表す専用の手段は無い（ https://pkg.go.dev/github.com/anishathalye/porcupine ）。そこで応答の時刻を履歴の末尾に置く。その操作はそれ以降のすべての操作と並行になり、検査器は最後に並べることもできるので、適用されなかった場合も説明できる。
- **テナント名**（ https://www.rfc-editor.org/rfc/rfc1123.txt §2.1、 https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/ 、 https://kubernetes.io/docs/concepts/overview/working-with-objects/names/ ）：RFC 1123 は、RFC 952 のホスト名の構文から先頭文字の制限を緩めて英字または数字とし、63 文字までの名前を扱うことを必須とする。Kubernetes は namespace 名に RFC 1123 の DNS ラベルを要求する。Kubernetes の現行の検証は先頭を英字に限るので、Kubernetes の namespace 名はすべて本 ADR のテナント名として通る。ラベルは `/` を含まないので、`/t/a/` と `/t/ab/` のように、あるテナントの接頭辞が別のテナントの接頭辞の先頭になることは無い。
- **リビジョンとコンパクションはクラスタ全体のもの**（`core/store/storetest/scope.go`）：既存の試験用ビュー `Scope` は「リビジョンとコンパクションは全体のままなので、ほかに書き込む者がいないことは呼び出し側が保証する」と書いている。etcd の `clientv3/namespace` もキーの接頭辞だけを付け外しする（ https://pkg.go.dev/go.etcd.io/etcd/client/v3/namespace ）。
- **etcd の RBAC**（ https://etcd.io/docs/v3.6/op-guide/authentication/rbac/ ）：ロールにはキー接頭辞（範囲 `[/foo/, /foo0)`）への read・write・readwrite を与えられる。権限の境界を etcd 側に置くことは可能だが、本 ADR では使わない。
- **版**（ https://etcd.io/blog/2026/oct-22-patch-release/ ）：CI とモジュールが固定している v3.6.16 は 2026-10-22 のパッチリリースである。
- **比較だけの `Txn` は定足数読み取りを通らない**（ https://github.com/etcd-io/etcd/blob/v3.6.16/server/etcdserver/v3_server.go 、 https://github.com/etcd-io/etcd/blob/v3.6.16/server/etcdserver/txn/txn.go ）：`EtcdServer.Txn` は、読み取り専用の `Txn` を `IsTxnSerializable` が偽のときだけ `linearizableReadNotify` に通す。`IsTxnSerializable` は成功側と失敗側の操作をすべて調べるので、どちらも空なら真を返す。その `Txn` は応答したメンバーの状態だけで評価される。3 メンバーに対する DRT が、書き込みの直後に 2 つ古いリビジョンを返す例を 1,000 ケース中 1 件で検出した。フォロワーを一時停止する回帰テストは、修正前は 3 回中 3 回失敗し（200 リビジョン古い応答）、修正後は 10 回中 10 回通った。
- **開始リビジョン 0 の watch はメンバー自身のリビジョンから始まる**（ https://github.com/etcd-io/etcd/blob/v3.6.16/server/storage/mvcc/watchable_store.go ）：`watchableStore.watch` は、`startRev` が 0 のとき `minRev` を `s.store.currentRev + 1` にする。これは応答したメンバーのリビジョンである。契約は、`fromRev` が 0 の watch を「呼び出しのあとの最初の変更から」と定める。3 メンバーに対する DRT が、直前に確定した変更を配信する例を、1,000 ケースの実行 4 回のうち 1 回で検出した。回帰テストは、修正前は 3 回中 3 回失敗し、修正後は 10 回中 10 回通った。
- **未来の開始リビジョンを持つ watch に etcd は進捗を返さない**（同じ `watchable_store.go` の `progressIfSync`）：ストアのリビジョンが watch の `startRev` より小さいあいだ、進捗要求は答えられない。読んだリビジョンの次から etcd の watch を開く修正は、書き込みの無いストアで進捗要求が永久に答えられず、DRT が全シードで時間切れになった。そのため開始リビジョンは 0 のままにし、古い変更を捨てる方式にした。
- **コンパクション済みのリビジョンからの watch も、メンバー自身の状態で判定される**（同じ `watchable_store.go` の `watch`）：開始リビジョンがメンバーの現在のリビジョンより大きい watch は、同期済みとして登録され、コンパクションとの照合を受けない。フォロワーを一時停止し、残りの 2 メンバーに 50 回書いてからコンパクションし、そのフォロワーに最初のリビジョンからの watch を開くと、修正前は 8 回中 7 回、`ErrCompacted` で終わらずに 50 件を配信した。
- **`Watch` の中の読み取りと期限**（`core/store/storetest/contract.go` の `testEndedWatchReportsItsError`）：契約テストは、期限 1 ms のコンテキストで `Watch` を 50 回呼び、`Watch` が watch を返したうえで、その watch が期限の誤りで終わることを求める。
- **1 台の停止では watch は終わらない**：`TestWatchAcrossMemberFailures` を 3 回実行し、どの回も watch は一度も終わらなかった。接続先のメンバーが止まると、clientv3 が別のメンバーへつなぎ直して watch を続けるためである。試験が自分で watch を終わらせて開き直すようにしたあとは、5 回の実行で 21〜26 回ずつ開き直した。開き直す位置を 1 つ手前にすると重複で、1 つ先にすると欠落で、試験は失敗した。
- **試験クラスタのポート**：以前は、空きポートを調べて閉じてから etcd を起動していた。そのあいだと、停止したメンバーを再起動するまでのあいだに、カーネルが同じポートを別のプロセスの空きポート要求に渡しうる。確保したブロックをファイルロックで占有する方式にしてから、etcd を使う試験を同時に 4 本走らせても衝突しなかった。
- **相乗り計測の実行例**（2026-11-18、開発機のループバック上、fsync なし、各 2 秒、強整合側 50 件／秒、ホット側 8 並列）：ホット側の書き込みが無いとき、強整合側の `Txn` は p50 1.6 ms・p99 2.5 ms、watch の配信は p50 1.5 ms・p99 2.3 ms だった。ホット側が 2 秒で 25,763 件を書いたとき、`Txn` は p50 0.8 ms・p99 2.8 ms、watch は p50 0.7 ms・p99 2.0 ms だった。この条件では相乗りによる悪化は読み取れなかった。1 回の実行であり、fsync を省いているので、運用時の値の根拠にはならない。
- **etcd 本家の分断の注入は、分離が不完全である**（ https://github.com/etcd-io/etcd/blob/v3.6.16/tests/robustness/failpoint/network.go 、 https://github.com/etcd-io/etcd/blob/v3.6.16/tests/framework/e2e/cluster.go 、 https://github.com/etcd-io/etcd/blob/v3.6.16/pkg/proxy/server.go ）：本家の堅牢性試験は、メンバーが広告するピア URL の前に `pkg/proxy` の TCP プロキシを置き、`BlackholeTx` と `BlackholeRx` で通信を捨てる。`network.go` は、この方法では「メンバーが相手とのあいだに pipeline を持つので、ピア通信はまだ可能である」と書き、全通信を止める方法を TODO にしている。メンバーのプロキシが扱うのは、そのメンバーへ張られた接続だけであり、そのメンバーが自分から張る接続は相手のプロキシを通るためである。相手のプロキシは、その接続を残りのメンバーからの接続と見分けられない。本家の e2e の枠組みは、ピア TLS の無い構成でこのプロキシを使うと「不正なパケットになりうる」として panic する。
- **Raft のメッセージを運ぶ要求は、すべて送信元のメンバー ID を持つ**（ https://github.com/etcd-io/etcd/blob/v3.6.16/server/etcdserver/api/rafthttp/util.go 、 https://github.com/etcd-io/etcd/blob/v3.6.16/server/etcdserver/api/rafthttp/stream.go 、 https://github.com/etcd-io/etcd/blob/v3.6.16/server/etcdserver/api/rafthttp/pipeline.go 、 https://github.com/etcd-io/etcd/blob/v3.6.16/server/etcdserver/api/rafthttp/snapshot_sender.go ）：pipeline とスナップショットの `POST` は `createPostRequest` が、ストリームの `GET` は `streamReader.dial` が、`X-Server-From` に自分のメンバー ID を入れる。ストリームは受け取る側が張り、相手はその応答の本体にメッセージを書く。したがって、あるメンバーのプロキシで「送信元がメンバー A の要求」を止めれば、A からそのメンバーへの pipeline と、そのメンバーから A へのストリームの両方が止まる。組の両側のプロキシで止めれば、その組の Raft のメッセージは両方向とも止まる。死活の探査（`/raft/probing`）は同じ RoundTripper を使うので、Raft の要求と同じ接続に乗りうる。そのため送信元は接続ごとではなく、要求ごとに読む。
- **少数派の側の挙動**（ https://github.com/etcd-io/etcd/blob/v3.6.16/server/embed/config.go 、 https://github.com/etcd-io/etcd/blob/v3.6.16/server/etcdserver/bootstrap.go 、 https://github.com/etcd-io/etcd/blob/v3.6.16/server/etcdserver/api/v3rpc/interceptor.go ）：既定値は `TickMs` 100、`ElectionMs` 1000、`PreVote` 真であり、Raft は `CheckQuorum` を真にして起動する。`monitorLeader` は選挙タイムアウト（既定 1 秒）ごとにリーダーの有無を調べ、3 回続けてリーダーが無いと、リーダーを要求するストリームをすべて `ErrGRPCNoLeader` で打ち切る。したがって、切り離されたメンバーに開いた watch が終わるまで、既定で 3 秒以上かかる。`etcdstore` は watch を `clientv3.WithRequireLeader` つきで開いている。
- **Jepsen の etcd 3.4.3 の分析**（ https://jepsen.io/analyses/etcd-3.4.3 、2020-01-30）：分断（1 台の切り離し、多数派と少数派の分割、推移的でない分断）、プロセスの停止と一時停止、時計のずれ、メンバー変更を注入し、KV の操作は厳密に直列化可能に見え、watch はすべての更新を順序どおりに届けた、と報告している。対象は 3.4.3 であり、3.6 の保証を直接示すものではない。一時停止は分断とは別の障害として扱われている。
- **ヘッダを持たないピアの経路**（ https://github.com/etcd-io/etcd/blob/v3.6.16/server/etcdserver/api/etcdhttp/peer.go ）：ピアの URL は、Raft の経路のほかに `/version`・`/members`・`/members/promote/`・`/downgrade/enabled`・`/members/hashkv`・`/leases`・`/leases/internal` と、`/raft/probing` を受ける。どれも Raft のメッセージを運ばないので、分断中に通しても、切り離したメンバーは新しい状態を得られない。`/leases` はリースの更新をリーダーへ運ぶが、[[0004]] の契約にリースは無い。一方、Raft の経路でヘッダの無い要求まで通すと、etcd がヘッダを変えたときに分断が黙って消える。そのため Raft の経路だけは、ヘッダが無ければ接続を切る。
- **自分から張った接続には読み書きのタイムアウトが効かない**（ https://github.com/etcd-io/etcd/blob/v3.6.16/client/pkg/transport/timeout_transport.go 、 https://github.com/etcd-io/etcd/blob/v3.6.16/client/pkg/transport/transport.go ）：`NewTimeoutTransport` は、読み書きの期限つきのダイアラを `http.Transport` の `Dial` に入れる。しかし `NewTransport` が先に `DialContext` を入れており、`net/http` は両方あると `DialContext` を使う。したがって、ストリームの読み手と pipeline の接続は、相手が黙っても自分からは切れない。止めた接続を分断を解くときに閉じるのは、このためである。
- **clientv3 の再試行**（ https://github.com/etcd-io/etcd/blob/v3.6.16/client/v3/retry.go ）：`Range` は、サーバが応答できないあいだクライアントが再試行する。`Txn` は再試行しない。過半数を失っているあいだに始めた読み取りは、呼び出しの期限が回復をまたげば、回復のあとに成功する。決定 7 が、始めた時刻ではなく応答した時刻で成功を禁じるのは、このためである。
- **進捗通知はメンバー自身のリビジョンを運ぶ**（`watchable_store.go` の `progressIfSync`）：切り離したメンバーや遅れたフォロワーの watch に進捗を要求すると、そのメンバーのリビジョンが返る。それ以下の変更が配信済みであることは成り立つが、クラスタの最新のリビジョンとは限らない。`core/store/store.go` は進捗通知を「ストアのリビジョンを運ぶ」と書いており、文面とずれている。呼び出し側は必要なリビジョンの通知が届くまで再要求することになっているので、安全性は破れない。
- **プロキシの確認の試験の結果**（2026-11-18）：最初の実装は、送信元のメンバー ID を知る前に張られた要求を追跡していなかった。メンバーはクラスタの起動中にストリームを張るので、あとから切ってもそのストリームは止まらず、確認の試験は 3 回中 3 回失敗した（切り離したフォロワーのリビジョンが 6 から 56 に進み、リーダーも交代しなかった）。ヘッダを持つ要求をすべて最初から追跡するようにしたあとは、5 回中 5 回通った。
- **確認の試験が通す経路**（2026-11-18）：分断中に届いた新しい要求を渡すようにプロキシを書き換えると、etcd を使わない試験は失敗したが、etcd を相手にする確認の試験は 7 秒の分断でも通った。分断が沈黙であるあいだ、すでに張られたストリームは切れず、メンバーは新しい要求を出さないためである。新しい要求を止める経路は、etcd を使わない試験だけが確かめている。
- **開き直した watch と進捗通知**（2026-11-18）：最後の変更まで受け取った直後に、その次のリビジョンから watch を開き直すと、開始リビジョンがストアのリビジョンを超える。契約は、ストアのリビジョンが `fromRev` に届くまで進捗要求を捨ててよいと定めるので、書き込みが止まると進捗通知は返らない。試験の締めの同期がこれを待ち続け、負荷をかけた 36 回の実行のうち 3 回で時間切れになった（プロキシの有無によらない）。締めの同期は、ストアのリビジョンが watch の開始リビジョンより小さければ、届くものが無いとして進捗を待たないようにした。そのあとは、同じ負荷の 36 回の実行がすべて通った。
- **古い状態を返さないことの試験の結果**（2026-11-18）：決定 6 を入れる前のアダプタに戻すと、切り離したフォロワーでもリーダーでも、比較だけの `Txn` が分断の前の状態を成功として返し、試験は失敗した。過半数を失っているあいだの比較だけの `Txn` も成功し、決定 7 の試験も失敗した。`fromRev` が 0 の `Watch` から定足数読み取りだけを外すと、切り離したフォロワーの watch が分断の前のリビジョンの進捗通知を返し、試験は失敗した（リーダーを切り離した場合は、書き込みが確定する前に旧リーダーが退くので検出しない）。決定 6 のあとのアダプタでは、どの呼び出しも期限切れで終わった。
- **調査で挙がったが一次資料を確かめていないもの**：`pkg/proxy` の不完全な分離を報告する issue（etcd-io/etcd #17737）と、上の読み書きのタイムアウトの件を報告する issue（#22638）。本 ADR の決定は、issue ではなく上のソースを根拠にする。

## 検討した代替案

- **メンバー 1 台の試験を残し、3 メンバーの試験を足す**：原因の切り分けはしやすい。しかし [[0005]] が運用するのは 3 台構成だけであり、試験の時間とコードがほぼ倍になるため採らない。
- **DRT だけメンバー 1 台のままにする**：件数の多い DRT の時間を抑えられる。しかし Lean モデルとの一致を確かめる対象が、運用する構成と違うものになるため採らない。
- **障害を注入しない**：3 メンバーで起動するだけでは、3 台にする理由である耐障害性を確かめられないため採らない。
- **エラーで返った `Txn` を失敗として履歴から落とす**：適用済みの書き込みを履歴から消すことになり、正しい実装を線形化不能と誤判定するため採らない。
- **ビューも `store.Store` を満たし、`Compact` をそのまま通す**：既存の契約テストをそのままかけられ、`store.Store` を求める箇所にそのまま渡せる。しかし 1 つのテナントの `Compact` が全テナントの履歴を消すため採らない。
- **ビューは `store.Store` を満たすが、`Compact` は常にエラーを返す**：どこにでも渡せる。しかし契約が定める `Compact` の意味から外れた実装を `store.Store` として流通させることになるため採らない。
- **ビューがテナントごとにリビジョンを振り直す**：他テナントの書き込みがリビジョンに現れなくなる。しかし etcd のリビジョンはクラスタに 1 つであり、振り直しには書き込みごとの追加の状態と、[[0004]] の契約に無い意味論が要るため採らない。
- **テナント名を `/` と制御文字以外は自由にする**：柔軟である。しかし大文字小文字や Unicode 正規化の違いで見分けにくい名前を許し、Kubernetes の namespace との写像にも規則が要るため採らない。
- **テナントを不透明な固定長の ID にする**：改名に強い。しかしキーを見ても誰のテナントか分からず、名前との対応表が G0 から要るため採らない。
- **ホット領域用の `Store` の継ぎ目を先に置く**：G1 での差し替えは楽になる。しかし利用者のまだ居ない抽象になるため採らない。
- **相乗り計測に合否の閾値を置く**：[[0005]] は G0 の閾値を定めていない。試験は `--unsafe-no-fsync` のループバック上で走るので、絶対値は運用時の値を表さない。根拠の無い閾値を新設することになるため採らない。
- **`fromRev` が 0 の watch を、読んだリビジョンの次から開く**：捨てる処理が要らず単純である。しかし etcd は開始リビジョンが未来の watch に進捗を返さないので、契約の `RequestProgress` を満たせないため採らない。
- **`fromRev` が 0 の watch を、読んだリビジョンから開いて重複分を捨てる**：進捗は返る。しかし etcd はその watch を未同期として扱い、同期の周期を待つぶん watch の開始が遅れるため採らない。
- **開発用クラスタを宣言だけにして起動手段を置かない**：宣言と実際のクラスタが一致しているかを確かめる手段が無くなるため採らない。
- **空きポートを調べてから起動する方式のままにする**：コードは短い。しかし調べてから etcd が使うまでのあいだに、ポートを他のプロセスに取られうるため採らない。
- **分断と過半数喪失を [[0015]] のシミュレーションだけで扱う**（[[0019]] の決定）：実物の etcd に仕掛けを足さずに済む。しかしシミュレータは未選定で、etcd を載せられるかは分からない。それまでアダプタと etcd の挙動を確かめられないため採らない。
- **過半数喪失だけを注入し、分断は注入しない**：今ある停止と一時停止だけで足りる。しかし止めたメンバーは応答しないので、少数派に残って応答し続けるメンバーに対するアダプタの挙動を確かめられないため採らない。
- **etcd 本家の `pkg/proxy` で分断する**：本家が保守しており、依存を 1 つ足すだけで済む。しかし本家自身が全通信を止められないと書いており、分断が起きていないのに試験が通る恐れがある。本家の e2e の枠組みは、平文のピア通信でこのプロキシを使う構成を panic で拒んでもいるため採らない。
- **`iptables` やネットワーク名前空間で分断する**：カーネルの層で切るので分離は確実であり、接続の確立の失敗や片方向の分断も再現できる。非特権のユーザー名前空間は `lake comparator` のためにすでに前提にしている。しかし、試験のプロセスを名前空間の中で実行し直し、メンバーごとの名前空間・仮想インタフェース・nftables の規則を組む仕掛けと、外部コマンドへの依存が要る。確かめたい性質は標準ライブラリだけのプロキシで現れるため、今は採らない。
- **プロキシが接続を切って分断を表す**：実装は単純である。しかし実際の分断では相手は切断を受け取らず、応答が無いことしか分からない。切断はすぐに検知されるので、検知が遅れる経路を通らないため採らない。
- **送信元を、接続の最初の要求だけで決める**：要求ごとに読むより単純である。しかし死活の探査は送信元のヘッダを持たず、Raft の要求と同じ接続に乗りうるため採らない。
- **ヘッダを持たない要求をすべて通す**：プロキシは単純になる。しかし etcd がヘッダを変えると、Raft の要求もすべて通り、分断が黙って消えるため採らない。
- **片方向だけの分断も注入する**：プロキシは方向を見分けられるので実現はできる。しかし確かめたい性質（少数派のメンバーが古い状態を成功として返さないこと）は、両方向の分断で現れる。試験の組み合わせが増えるため、今は採らない。

## 影響とトレードオフ

- **得るもの**：[[0005]] の構成（3 メンバー・テナント接頭辞・相乗り）を、契約テスト・線形化可能性検査・DRT が直接の対象にする。1 台の停止、リーダー交代、過半数の喪失、分断をまたいで契約が保たれることを機械判定できる。少数派に残ったメンバーが古い状態を返さないことを、実物の etcd で確かめられる。切り離されたメンバーの watch が誤りで終わる経路を、試験が通る。テナントのコードはクラスタ全体のコンパクションに触れない。
- **失うもの**：メンバー 1 台での切り分けはできなくなる。etcd を使う試験は 3 プロセスとプロキシを起動するぶん遅くなり、分断の試験は選挙タイムアウトの数倍を待つ。ピア通信は常にプロキシを通るので、試験クラスタの遅延はその分だけ増える。比較だけの `Txn` とすべての `Watch` は、定足数読み取り 1 回のぶん遅くなる。テナントビューは `store.Store` ではないので、`store.Store` を求めるコードにはそのまま渡せない。テナントからは他テナントの活動量がリビジョンの進みとして見える。
- **引き受けるリスク**：
  - プロキシは自前のコードであり、誤りがあれば分断が起きていないのに試験が通る。決定 8 の確認の試験でこれを抑える。
  - 分断の方式は etcd の内部（`X-Server-From` ヘッダと、平文の HTTP/1.1 のピア通信）に依存する。etcd の版を上げたときに、確認の試験が落ちることがある。
  - 障害注入の試験は時間に依存し、不安定になる恐れがある。失敗は乱数のシードからは再現しない。etcd の選挙と障害の時刻がシードで決まらないためである。
  - 切り離したメンバーの進捗通知が運ぶリビジョンは確かめていない。契約の文面とのずれ（根拠を参照）は本 ADR では直さない。
  - 相乗り計測の数値は fsync を省いたループバック上のもので、G1 の判断にそのまま使えない。根拠に挙げた実行例はプロキシを入れる前のものであり、今の試験クラスタではピア通信がプロキシを通るぶん遅延が乗る。
  - [[0006]] が `/t/<tenant>/` 以外の最上位を選べば、ビューの接頭辞を変えることになる。
- **今後の検証ゲート**：G0 で、3 メンバーのクラスタに対する契約テスト・線形化可能性検査（1 台の停止・過半数喪失・分断の注入あり）・DRT 1,000 ケース以上が通ることを確かめる。プロキシの確認の試験が、切り離しのたびに分断を観測することを確かめる。G1 で、相乗り計測を fsync を有効にした実機に対して行い、[[0005]] の watch p99 1 秒以内と照らす。1 組だけの分断・片方向の分断・遅延・時計のずれを実物の etcd に入れるかは、後続の ADR で決める。
