# 0005: G0〜G1 はテナント接頭辞をつけた単一の etcd v3.6 クラスタで運用する

## コンテキスト

[[0004]] でストア契約を固定した上で、G0〜G1 で実際に稼働させる強整合ストアとホット領域（イベント・エンドポイント等の再生成可能なデータ）の初期構成を定める必要がある。

[[0001]] の前提 6・7 により、個人＋AI の体制では検証ゲート（G0〜G2）ごとに仮説を確かめながら進めるべきであり、G0 の段階から分散合意ストアを自前開発すると本筋の差分オラクルや所有権検証の着手が遅れる。一方、[[0006]] のキー空間により全テナントは `/t/<tenant>/` 配下に分離されるため、論理境界を保ったまま物理構成を段階的に切り替えられる。

## 決定

1. G0〜G1 の強整合ストア層は、外部の単一 etcd v3.6 系クラスタ（3 台構成）とし、全テナントのデータを `/t/<tenant>/` 接頭辞（[[0006]]）の下に格納する。
2. G0 ではホット領域も同じ etcd クラスタに相乗りさせる（G1 で別層への分離を検証する）。
3. G2 では [[0004]] の同一契約テスト・線形化可能性検査の下で、次の 3 案を比較計測し、後続 ADR で選定する：
   - テナント群ごとの etcd クラスタ分割
   - `etcd-io/raft`（v3.7.0）と `cockroachdb/pebble`（v2.1.7）による自作ストア
   - FoundationDB と自作 watch 層の組み合わせ
4. watch 遅延が規模に対して線形に増加し、原因が etcd にあると判明した場合は、etcd のテナント群分割を前倒しする。自作 Raft ストアの実装は G2 より前には着手しない。

## 根拠（調査結果・出典）

- 内部不変条件：[[0004]] の `Store` 契約と [[0006]] の `/t/<tenant>/` 接頭辞により、上位層は単一クラスタか分割クラスタかを意識せず、接頭辞単位でストアを移行できる。
- etcd のリリース状況（ https://etcd.io/blog/2026/oct-22-patch-release/ ）：2026-10-22 に v3.7.3・v3.6.16・v3.5.35 がリリースされたことを確認した。保守の方針（ https://etcd.io/docs/v3.7/op-guide/versioning/ ）は、現行版と直前 2 つのリリースのブランチを保守するというもので、v3.7 が現行の今は v3.6 と v3.5 が対象であり、v3.5 は v3.8 のリリースで保守から外れる。同ページは保守終了の日付を示していない（なお `docs/research/draft_20261117_001.md` §2.3 の「月次パッチ」という記述とは異なり、パッチの周期を定めた記述は無い）。v3.6 系を G0〜G1 の標準とする。
- FoundationDB の制約（ https://apple.github.io/foundationdb/known-limitations.html ）：1 トランザクションあたり影響データ上限が 10,000,000 バイト（1 MB を超えるなら設計の見直しを推奨）、5 秒を超えるトランザクションは扱えず読み取りが `transaction_too_old` となることを確認した。watch は開発者ガイド（ https://apple.github.io/foundationdb/developer-guide.html ）に指定したキーに対して作るものとして書かれており、範囲に対する watch の記載は確認できなかった。大きなテナントや LIST の分割層と watch 層の自作が避けられないため、G2 の比較対象に下げる。
- G2 比較候補のライブラリ版：`etcd-io/raft` v3.7.0 および `cockroachdb/pebble` v2.1.7 を確認した。
- 規模・遅延の目標値（`docs/research/draft_20261117_001.md` §8.2・§8.3）：G1 で実機 100＋模擬 10,000 ノード（watch p99 1 秒以内、ノードあたり制御面 CPU が 1,000 ノード時の 1.5 倍以内）、G2 で実機 1,000＋模擬 50,000 ノード・1,000 テナント（watch p99 1 秒以内・10,000 ノード時の 1.2 倍以内）はいずれも初期値とする。

## 検討した代替案

- **最初から FoundationDB を採用する**：10,000,000 バイト・5 秒制限を回避する分割層と範囲 watch の自作が G0 から必要になり、自作合意ストアに近い開発負荷が発生するため採らない。
- **最初から `etcd-io/raft`＋`pebble` で自作 Raft ストアを作る**：G0 で優先すべき形式仕様・DRT・Kubernetes 差分ハーネスの整備より先に分散ストレージ開発を抱え込むため採らない。
- **最初からテナントごとに独立した etcd クラスタを立てる**：小規模な G0〜G1 からクラスタ群の自動生成・運用・バックアップを抱えることになり過剰なため採らない。
- **SQL バックエンド上の `kine`（ https://github.com/k3s-io/kine ）を採用する**：`kine` が etcd v3 gRPC API のサブセットを SQL 上に実装していることは確認したが、Nayutar が目標とする数万ノード・多テナント規模での書込み競合や水平拡張特性は未確認であるため、G0〜G1 の標準には採らない。

## 影響とトレードオフ

- **得るもの**：G0〜G1 で実績ある強整合ストアをそのまま利用し、API・所有権・[[0007]] の watch キャッシュ・検証基盤の開発に資源を集中できる。
- **失うもの**：単一クラスタの書込みスループットと MVCC 履歴容量がテナント間で共有され、巨大テナントを物理隔離する能力は G2 または分割前倒しまで得られない。
- **引き受けるリスク**：G1（模擬 10,000 ノード）の達成前に単一 etcd クラスタが飽和し、分割の前倒しが必要になる恐れがある。また G0 ではホット領域も etcd に載せるため、高頻度イベントが合意遅延を押し上げる可能性がある。
- **今後の検証ゲート**：G1 で模擬 10,000 ノード時の watch p99 遅延と制御面 CPU 増加率を計測し、G2 で模擬 50,000 ノード・1,000 テナントの定数性と 3 候補の契約テスト比較を行う。watch 遅延が線形増加し etcd が原因と特定された場合は分割を前倒しし、G2 の計測結果に基づき後続 ADR で本決定を更新する。
