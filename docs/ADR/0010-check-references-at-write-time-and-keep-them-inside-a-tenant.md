# 0010: Ref の解決先をテナント内に閉じ込め書き込み時に認可と型を検査する

## コンテキスト

[[0001]] で宣言基盤に定めた LKAL v0.1 には、すでに `Ref` 値型（例：`&secret/db-creds/password`、LKAL-JSON では `{"$ref":"secret/db-creds/password"}`）が存在する。一方、[[0006]] のとおり Nayutar はテナントをキー空間の最上位に置き、namespace を隔離単位にしない。`Ref` にテナントを越える表記を許したり、参照先の検査をコントローラの実行時まで遅らせたりすると、利用者が書けないはずの資源をコントローラ権限で代理読み書きさせる越境攻撃が起きる。そのため LKAL 既存の `Ref` 値に対する API サーバ側の検査規則を固定する必要がある。

## 決定

LKAL 本体の仕様には手を加えず、API サーバは `Ref` 値を含む書き込みとコントローラの読み取りに対して次を強制する。

1. 更新前後のオブジェクトを比較し、新たに追加された `Ref` の集合を算出する。
2. 追加された各 `Ref` について、テナント内の相対名のみを許可し、テナントを越える表記を拒否する。
3. 参照先を当該テナント内で解決する。`Binding` 種別のリソースは `identityHash` 付きで解決する。
4. Cedar によりアクション `Reference`（対象リソース、および `sourceKind`・`sourcePath`）の認可を評価し、拒否された場合は書き込み全体を失敗させる（fail-closed）。
5. スキーマが当該フィールドに許可する参照先 `kind` 以外は拒否する。
6. [[0006]] で定めた逆参照索引の更新を、オブジェクト本体の書き込みと同じ CAS トランザクション（[[0004]]）に含める。
7. コントローラが読み取れるオブジェクトは、自身が `Binding` で権限を持つオブジェクトから `Ref` で参照されているものに限る。

この検査により、NDSS 2026 が分類した 2 つの攻撃類型のうち、安全でない namespace 間参照を悪用する型は項目 2・4・7 で塞ぎ、安全でないクラスタ全体参照（`ClusterRoleBinding` や `Namespace` を作らせる型）を悪用する型はクラスタ全体ロールと namespace の不在および項目 4・5 により成立しないようにする。

## 根拠（調査結果・出典）

- LKAL（`https://github.com/Kaikei-e/LKAL`）の `docs/PRINCIPLE.md`（2026-11-17 確認）：LKAL v0.1 にすでに `Ref` 値型と LKAL-JSON の `$ref` 表現が存在することを確認した。よって `docs/research/draft_20261117_001.md` §6.5・§10 にあった「Ref を新規追加提案とする」前提は修正し、サーバ側検査のみを決定する。
- NDSS 2026「Breaking the Bulkhead」（https://www.ndss-symposium.org/ndss-paper/breaking-the-bulkhead-demystifying-cross-namespace-reference-vulnerabilities-in-kubernetes-operators/ 、https://arxiv.org/abs/2507.03387 ）：Go 製 Operator 2,268 件の解析で 318 件（14% 超）が潜在的に脆弱、8 件が確認され CVE 7 件が発行された。安全でない namespace 間参照が 196 件、クラスタ全体参照が 175 件あり、33 Operator で `ClusterRoleBinding` 作成、29 Operator で `Namespace` 作成が誘発可能であることを確認した。
- kcp 公式ドキュメント（https://docs.kcp.io/kcp/main/concepts/apis/exporting-apis/ ）：`APIExport` / `APIBinding`（`apis.kcp.io/v1alpha2`）では identity key を秘密に保ち `identityHash` を公開し、他 Export の資源への権限要求には `identityHash` が必須で利用者が `APIBinding` で個別に受理・拒否することを確認した。
- cedar-go（https://github.com/cedar-policy/cedar-go ）：Go 実装の Cedar 認可エンジンとして v1.9.x が存在することを確認した。
- `docs/research/draft_20261117_001.md` §2.2・§6.5：書き込み時アルゴリズムと攻撃類型への対応に基づく。

## 検討した代替案

- **Kubernetes のように読み取り時・reconcile 時に遅延解決する**：書き込み順序の制約が緩くなる。しかし書き込み者が持たない権限の対象をコントローラが後から代理参照でき、NDSS 2026 で示された越境攻撃の構造をそのまま残すため採らない。
- **参照先側に `ReferenceGrant` 型のオプトイン資源を置く**：明示的許可の一方式になり得る。しかし認可の判断経路を Cedar と `Binding` に一本化する方が監査しやすく、また `ReferenceGrant` の詳細仕様自体は未確認であるため採らない。
- **明示的な許可があればテナントを越える `Ref` を許す**：テナント間連携の記述は直接的になる。しかし [[0006]] のテナント最上位キー空間による隔離境界を破り越境検査が複雑化するため、越境は `Binding` に限定し `Ref` はテナント内に閉じる。
- **`Ref` 型を使わず通常の文字列で参照を書く**：型や構文は単純に見える。しかしどの文字列が参照かを構文から機械的に抽出できず、汎用的な書き込み時認可と逆参照索引の維持が成り立たないため採らない。

## 影響とトレードオフ

- **得るもの**：`Ref` の越境と未認可参照を書き込み時点で構造的に遮断でき、逆参照索引（[[0006]]）を本体と同一 `Txn`（[[0004]]）で整合させられる。
- **失うもの**：参照先の存在や権限なしに先行参照を書く運用や、テナントを越える直接 `Ref` はできない。また新規 `Ref` を含む書き込みごとに Cedar 評価と索引更新の負荷が加わる。
- **引き受けるリスク**：`cedar-go` v1.9.0 時点でポリシーテンプレートが未実装（`docs/research/draft_20261117_001.md` §2.3）のため、テナント既定ポリシーの管理負担が増えるおそれがある。参照先の削除や権限剥奪後に既存 `Ref` へどう再評価をかけるかはコントローラ側の設計課題として残る。
- **今後の検証ゲート**：G0 で `Ref` の負の試験（越境表記・未許可 `kind`・Cedar 拒否時の全体ロールバック）を実施する。G2 で NDSS 2026 の 2 戦略を翻案した攻撃がすべて拒否されることを検証し、突破経路や重大な遅延が確認された場合に本決定を再検討する。
