# 0026: 参照の検査を、純粋な検査の核・参照のスキーマ表・Cedar の認可・オブジェクトの Txn に入る逆参照索引で実現する

## コンテキスト

[[0010]] は、API サーバが `Ref` を含む書き込みに強制する 7 項目を決めた。追加された `Ref` の算出、テナントを越える表記の拒否、テナント内での解決、Cedar による `Reference` の認可、スキーマによる参照先 `kind` の検査、逆参照索引の同一 `Txn` での更新、コントローラの読み取りの制限である。実装に要る次の点は決めていない。

- `Ref` のセグメント列のどこまでが参照先で、どこからが葉パスか。「テナントを越える表記」とは何か。
- 「追加された `Ref`」を何の差で数えるか（値か、置き場所と値の組か）。
- `Ref` を置ける場所（`spec`・`status`・`meta`）。
- 「スキーマ」の形。スキーマはまだ無い（[[0025]]）。
- Cedar のエンティティの形（principal・resource・context）、ポリシーの出どころ、評価の誤りの扱い。
- 検査の順序と、どこまでを 1 回の `Txn` で確かめるか。
- 逆参照索引の値、削除のときの扱い、1 回の `Txn` の大きさ。

`Binding`（`/t/<tenant>/bind/<identityHash>`）、Export（`/x/<identityHash>/`）、コントローラはまだ無い。

本 ADR は [[0010]] の実現方式を決める。[[0010]] の項目 3 のうち `Binding` 種別の `identityHash` つきの解決と、項目 7 のコントローラの読み取りの制限は、Export と `Binding` を決める ADR に残す。HTTP の API サーバ、認証、ポリシーの保存と管理、Patch（[[0012]]）、所有権（[[0013]]）も扱わない。

## 決定

1. **`Ref` は `&<修飾つき kind>/<name>` に、任意の葉パスが続く形に限る。** LKAL の `Ref` はセグメントの列であり、次のとおりに読む。
   - 第 1 セグメントは修飾つき kind である。文法は [[0022]] の `ref/` と同じで、group が `core` なら `<kind>`、それ以外は `<kind>.<group>` と書く。
   - 第 2 セグメントは `<name>`（[[0022]] の DNS サブドメイン）である。
   - 第 3 セグメント以降は参照先の文書の中の葉パスで、無くてよい。ある場合、最初のセグメントは `meta`・`spec`・`status` のどれかで、どのセグメントも空でなく、`/` を含まず、`$` で始まらない。
   - これ以外の形はすべて形の誤りとして拒否する。テナントを指す表記は文法に無く、どの `Ref` も書き込み先のテナントの中の相対名としてだけ読む。`&t/<tenant>/o/...` のようにキーをまねた表記は、葉パスの先頭が `o` なので拒否される。
   - 解決するのはオブジェクトである。葉パスは文法だけを検査し、参照先にその葉があるかは確かめない。
2. **`Ref` は `spec` の中にだけ置ける。** 検査は書き込みの結果の文書全体を調べ、`spec` の外に `Ref` があれば形の誤りとして拒否する。`meta` は [[0025]] の形により `Ref` を持てない。したがって `UpdateStatus` は `Ref` を追加できない。
3. **出現を「置き場所と値の組」で数え、追加分だけを検査する。**
   - 出現は `(sourcePath, ref)` の組である。置き場所は、文書の根から `Ref` を値に持つ欄までのキーの列である。リストの要素の置き場所は、リストを値に持つ欄のキーの列（`spec`・`volumes`）とする。
   - 置き場所のキーは、空でなく `/` を含まないものに限る。LKAL のレコードのキーは `/` も空文字列も持てるので、この制限が無いと `spec`・`db`・`password` と `spec`・`db/password` が同じ文字列になり、許された `Ref` を別の欄へ移しても追加と数えずに済んでしまう。制限により、キーを `/` で連結した `sourcePath`（`spec/db/password`）は置き場所を一意に表す。
   - 追加された出現は、結果の `spec` の出現の集合から、保存済みの `spec` の出現の集合を引いたものである。作成では保存済みを空とする。同じ `Ref` を別の欄へ移すと、追加として検査する。
   - 追加でない出現は検査し直さない（[[0010]] の「既存 `Ref` の再評価はコントローラ側の設計課題」のとおり）。
4. **参照のスキーマ表を設定で渡す。**
   - 表は、参照元の修飾つき kind ごとに規則の列を持つ。規則は、パスの型（セグメントの列。先頭は `spec`。`*` はちょうど 1 セグメントに合う）と、許す参照先の修飾つき kind の集合の組である。
   - 出現が許す参照先は、`sourcePath` に合うすべての規則の集合の和である。和が参照先の kind を含まなければ拒否する。
   - 表に無い kind の文書と、どの規則にも合わない場所にある `Ref` は拒否する（fail-closed）。
   - 表の保存と、LKAL v0.2 のスキーマとの関係は、スキーマを決める ADR に残す。
5. **認可は cedar-go で行い、要求の形を固定する。**
   - principal：書き込む側が渡す型と ID の組（`Nayutar::User::"alice"` など）。認証は扱わず、呼び出し側を信じる。型か ID が空なら拒否する。
   - action：`Nayutar::Action::"Reference"`。
   - resource：`Nayutar::Object::"<tenant>/<修飾つき kind>/<name>"`。UID にテナントを入れるのは、同じポリシー集合を複数のテナントで使っても、別のテナントの同じ名前のオブジェクトと区別するためである。参照先があるときは、属性 `tenant`・`kind`（修飾つき kind）・`name`・`labels`（String のレコード。ラベルが無ければ空のレコード）を持つエンティティを渡す。参照先が無いとき、または値が読めないときは、このエンティティを渡さない。
   - context：`tenant`・`sourceKind`（参照元の修飾つき kind）・`sourceName`・`sourcePath`。
   - ポリシー集合と principal 側のエンティティは設定から渡す。設定のエンティティに、`Nayutar::Object` 型のもの、親や属性に `Nayutar::Object` の UID を持つものがあれば、結合を作るときに拒否する（`principal in resource` を設定から成り立たせないため）。どのポリシーも許さなければ拒否する。
   - 決定が `Allow` で、かつ評価の誤り（`Diagnostic.Errors`）が 1 つも無いときだけ許す。cedar-go は評価が誤ったポリシーを飛ばすので、そのままでは書き損じた `forbid` が黙って効かなくなる。
   - 要求は葉パスを含まないので、`(sourcePath, 参照先)` が同じ出現には 1 回だけ問い、結果を使い回す。同じ参照先でも `sourcePath` が違えば別の要求である。
6. **検査の順序を固定する。** 誤りは 5 種類（`internal`・`malformed`・`kind`・`denied`・`notFound`）である。封筒の遷移（[[0025]]）が受け付けた結果に対して次の順に調べ、最初に当たった段の誤りを返す。同じ段で複数の出現が当たるときは、`sourcePath` のバイト列、続いて `ref` のセグメント列の辞書順で最小の出現を返す。
   1. 保存済みの文書に、`spec` の外の `Ref`、置き場所のキーが空か `/` を含む `Ref`、文法に合わない `spec` の `Ref` のどれかがある → `internal`。保存済みの `spec` が参照する異なるオブジェクトが 32 を超える → `internal`（出現は示さない）
   2. 結果の文書に、`spec` の外の `Ref` か、置き場所のキーが空か `/` を含む `Ref` がある → `malformed`
   3. 追加された出現が文法に合わない → `malformed`
   4. 結果の `spec` が参照する異なるオブジェクトが 32 を超える → `malformed`（出現は示さない）
   5. スキーマ表が許さない → `kind`
   6. 認可が許さない → `denied`
   7. 参照先が無い → `notFound`

   段 1 が保存済みの文書の誤りを `internal` にするのは、`Objects` を通らずに書かれた値が原因であり、書き手の誤りではないからである。`Update` は `status` を保存済みから引き継ぐので、`status` に `Ref` を持つ保存済みの文書は段 1 で止まる。段 1 に当たる文書は、決定 8 の「読めない」文書と同じであり、`Update` でも `UpdateStatus` でも直せず、削除の走査の経路でだけ消える。これにより、走査で索引を消している途中に、同じ文書への書き込みが索引を前提にして成功することが無い。

   認可を存在の確認より前に置くのは、認可されない書き手に「無い」と「拒否」の差から名前の有無を探らせないためである。ただし、参照先の属性の有無で判定を変えるポリシー（`resource has labels` を条件に含むものなど）は、その判定の差から有無を伝えうる。これを避けるのはポリシーを書く側である。[[0010]] の項目の並び（解決 → 認可 → kind）とは順が違うが、検査する項目の集合は同じである。
7. **検査の核を純粋なパッケージ `core/resource/refs` に置き、2 段の API にする。**
   - 核は、文法、出現の収集と差、スキーマ表、検査の順序、索引の差分を持ち、ゴルーチン・時計・ストア・Cedar を持たない。値の木には LKAL の Go モジュールの型を使う。
   - 第 1 段（`Prepare`）は、保存済みの文書と結果の文書から段 1〜5 を調べ、追加された出現と、読むべき参照先を返す。
   - 第 2 段（`Check`）は、認可と存在の判定を受け取って段 6〜7 を調べ、索引の差分と比較する参照先を返す。呼び出し側が文法を二重に実装しないように、読むべき参照先は第 1 段が決める。
8. **逆参照索引は、参照先と参照元のオブジェクトの組ごとに 1 キーとする。**
   - キーは [[0006]]・[[0022]] の `/t/<tenant>/ref/<tQKind>/<tName>/<sQKind>/<sName>`、値は空のバイト列である。参照元が同じ参照先を何か所から指しても 1 キーである。自分自身への参照も組に含める。
   - 書き込みでは、結果の `spec` の参照先の集合と保存済みの `spec` の参照先の集合の差を取り、増えた組を Put、減った組を Delete する。
   - `UpdateStatus` は `spec` を変えないので索引に触れない。結果が保存済みと `Equal` なら何も書かない（[[0025]]）。
   - 削除では、保存済みの文書が「読める」とき、本体の削除と、保存済みの `spec` の参照先の組の削除を、本体の比較を付けた 1 回の `Txn` で行う。「読める」とは、[[0025]] の読み出し（復号、保存済みの形、キーとの同一性）を通り、段 1 に当たらず、参照先が 32 以下であることである。
   - 読めないとき（[[0025]] は読めない値も消せる）は、テナントの `ref/` の範囲を走査し、参照元がそのオブジェクトであるキーを集める。それらを、本体の比較を付けた `Txn` で何回かに分けて消し、最後に本体を消す。`ErrTooLarge` が返れば 1 回の個数を半分にしてやり直す（[[0022]] の登録簿の削除と同じ）。途中で止まった削除は、呼び直せば続きから進む。読めない文書は `Update` も `UpdateStatus` も誤りで返すので、途中の状態から索引が書き足されることはない。
   - 参照先を消しても、それを指す索引のキーと参照元の `Ref` は残る。参照先の削除は止めない。
   - 索引が参照元の文書と正確に一致するのは、そのテナントの書き込みがすべて `Objects` を通るときに限る。索引を権限の判断に使う後続の決定（[[0010]] の項目 7 など）は、参照元の文書で確かめ直す。
9. **ストア結合は、本体・索引・参照先の版を 1 回の `Txn` で確かめる。**
   - 書き込みの手順は、封筒の遷移（[[0025]]）→ 核の第 1 段 → 参照先の読み取り → Cedar の評価 → 核の第 2 段 → 結果が保存済みと `Equal` なら何も書かない → `Txn` である。
   - `Objects` は、第 1 段が返した参照先を 1 つにつき 1 回読む。読んだ値を Cedar の属性と存在の判定に使う。読めない値を持つ参照先は、認可では「無い」として扱い、存在の判定では「ある」として扱い、核が受け付けたあとで `internal` を返す。認可されない書き手に、読めない参照先の有無を `internal` で伝えないためである。
   - `Txn` の比較は、本体の比較（[[0025]]）に、比較する参照先それぞれの「mod revision が読んだ値に等しい」を足したものである。参照先が参照元そのものなら、本体の比較が同じことを確かめるので足さない（作成では、自分自身への参照は参照先がまだ無いので `notFound` になる）。比較が通らなければ競合として返し、再試行しない。
   - 操作は、本体の Put と、索引の Put・Delete である。検査のどれかに当たれば何も書かない。
   - 異なる参照先を 32 までにしたので、更新の `Txn` は比較が最大 34 個（登録簿のフェンスを含む）、操作が最大 65 個であり、etcd の既定の上限 128 に収まる。[[0013]] の所有権のキーを足す余地も残る。
   - `Create` と `Update` は principal を引数に取る。`UpdateStatus` と `Delete` は取らない。principal が要るのは Cedar に問うときだけで、追加された出現が無ければ空でもよい。設定に認可が無ければ、追加された出現はすべて `denied` になる。設定は、Cedar の要求に入れるテナント名を持つ（テナントのビューは自分の名前を持たない）。
   - 設定の誤りは黙って通さない。スキーマ表が検査（kind とパスの文法）を通らなければ、参照の検査に入る書き込みはすべて `internal` で返す。認可があるのにテナント名が文法に合わなければ、追加された出現を持つ書き込みを `internal` で返す。Cedar との結合も、テナント名・名前が文法に合わない要求を拒否する。
10. **Cedar との結合を `core/resource/refcedar` に置く。** cedar-go v1.9.3 に依存し、決定 5 の要求を組み立てて `cedar.Authorize` を呼ぶ。核とストア結合は Cedar の型を持たない。
11. **核を Lean モデルと照合し、検査の性質を定理にする。**
    - `spec/Nayutar/Refs.lean` に同じ規則を書き、`nayutar-drt` の `refs` スイートとして実行する。モデルでは、認可と存在は入力として与える判定（許す出現の集合、ある参照先の集合）である。
    - Go 側は、妥当な `Ref` とそれを壊した `Ref`、キーをまねた表記、スキーマに合う場所と合わない場所、認可と存在の組み合わせ、欄の順序の入れ替えを乱数で作る。成否・誤りの種類・誤りの出現・索引の差分・比較する参照先が Lean と一致することを確かめる。
    - モデルの上の定理 8 個（`Nayutar.Refs`）を保護の対象にする。「追加された出現」というモデルの定義に頼ると、その定義の誤りで主張が空虚に成り立つので、主張は文書の出現の水準で述べる。
      - `accepted_refs_well_placed`：受け付けたなら、結果の文書の `Ref` はすべて `spec` の中にあり、置き場所のキーは空でなく `/` を含まない。
      - `accepted_new_refs_checked`：受け付けたなら、結果の文書のどの出現も、保存済みの文書の出現であるか、文法に合い、スキーマ表がその参照先の kind を許し、認可の判定が許し、参照先がある。
      - `accepted_targets_bounded`：受け付けたなら、結果の `spec` の参照先は 32 以下である。
      - `index_delta_exact`：受け付けたなら、Put はちょうど「結果の参照先のうち保存済みに無いもの」、Delete はちょうど「保存済みの参照先のうち結果に無いもの」であり、どちらにも重複が無い。
      - `accepted_put_compared`：受け付けたなら、Put する参照先はすべて比較する参照先に含まれる。索引に新しく足す組の参照先は、同じ `Txn` で版を確かめている。
      - `denied_ignores_presence`：認可の判定が許さない追加された出現があるなら、検査の結果は存在の判定に依存しない。
      - `accepted_delta_valid`：受け付けたなら、Put・Delete・比較に現れる参照先はどれも、Keyspace モデルの修飾つき kind と `<name>` の文法に合う。
      - `delete_clears_index`：削除が受け付けられたなら、索引の差分は Put が空で、Delete がちょうど保存済みの参照先である。
    - 定理が述べるのはモデルである。Cedar の評価そのものは cedar-go の責任であり、モデルは判定を入力として受け取る。Go の核とは DRT で、ストア結合とは試験で結ぶ。

## 根拠（調査結果・出典）

- **書き込み時の検査は、論文の緩和策を API サーバに入れたものである**（NDSS 2026、 https://arxiv.org/html/2507.03387 §VI、2026-11-21 確認、agy ワーカーによる取得）：緩和策の Validating Admission Webhook は「evaluates whether the user has cross-namespace permissions by issuing a SubjectAccessReview query to the API Server」とし、権限が無ければ要求が Operator に届く前に拒否する。同節は、最小権限だけでは足りない理由を「our attack arises even when Operators follow PoLP」と書く。本 ADR は、この判定を書き込みの経路そのものに置く。
- **cedar-go の版と誤りの扱い**（手元のモジュールキャッシュで確認、2026-11-21）：`go list -m -versions github.com/cedar-policy/cedar-go` の最新は v1.9.3（2026-11-18T16:14:05Z 公開）で、`go.mod` は `go 1.26.0`、ライセンスは Apache-2.0 である。`authorize.go` の `Authorize(policies PolicyIterator, entities types.EntityGetter, req Request) (Decision, Diagnostic)` は、評価が誤りになったポリシーを `diag.Errors` に入れて `continue` し、真になった `forbid` が 1 つでもあれば `Deny`、そうでなく真になった `permit` があれば `Allow`、どちらも無ければ `Deny` を返す。決定 5 の「誤りがあれば拒否」はこの実装に対するものである。README は、Go 実装にまだ無いものとして「the schema validator (experimental support is provided in x/exp/schema ...)」「partial evaluation」「support for policy templates」を挙げる。
- **Txn の上限**（etcd v3.6.17 の `server/embed/config.go`、手元のモジュールキャッシュで確認、2026-11-21）：`DefaultMaxTxnOps = uint(128)`、`DefaultMaxRequestBytes = 1.5 * 1024 * 1024`。etcd の文書（ https://etcd.io/docs/v3.6/op-guide/configuration/ ）も `--max-txn-ops '128'` と書く（agy ワーカーによる取得）。決定 9 の 32 の根拠である。
- **参照先側のオプトインと取り消し**（Gateway API、 https://gateway-api.sigs.k8s.io/reference/api-types/referencegrant/ と https://gateway-api.sigs.k8s.io/reference/api-spec/1.7/spec/ 、2026-11-21 確認、agy ワーカーによる取得）：`ReferenceGrant` は参照先の namespace に置くオプトインであり、実装は「MUST NOT permit cross-namespace references which have no grant, and MUST respond to the removal of a grant by revoking the access that the grant allowed」とされる。本 ADR は別の資源を置かず、参照先の `labels` を Cedar の属性に渡して、同じオプトインをポリシーで書けるようにする。取り消しにあたる再評価は、[[0010]] のとおりコントローラ側に残る。
- **Kubernetes は参照を書き込み時に解決しない**（2026-11-21 確認、agy ワーカーによる取得）：`ownerReferences` の検査（ https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/apimachinery/pkg/api/validation/objectmeta.go の `validateOwnerReference`）は欄の形だけを見て、所有者の存在は確かめない。所有者が無いと、ガベージコレクタが後から「dangling」と判定する（ https://github.com/kubernetes/kubernetes/blob/master/pkg/controller/garbagecollector/garbagecollector.go ）。Crossplane の参照も reconcile のときに解決し、参照先が無ければ `CannotResolveRefs` を記録して再試行する（ https://github.com/crossplane/crossplane-runtime/blob/main/pkg/reference/reference.go ）。本 ADR は、これらが後に回す存在の確認を書き込みの `Txn` に入れる。
- **参照先の削除を止める汎用の仕組みは Kubernetes にも無い**（2026-11-21 確認、agy ワーカーによる取得）：PVC には `kubernetes.io/pvc-protection` のファイナライザがある（ https://kubernetes.io/docs/concepts/storage/persistent-volumes/ ）。汎用の「In-use protection」（ https://github.com/kubernetes/enhancements/issues/2839 ）は `lifecycle/frozen` のままで、KEP の PR（ https://github.com/kubernetes/enhancements/pull/2840 ）は 2025-12-27 にマージされずに閉じられた。本 ADR も参照先の削除を止めない。
- **`Binding` の解決には identityHash が要る**（kcp、 https://docs.kcp.io/kcp/v0.33/concepts/apis/exporting-apis/ 、2026-11-21 確認、agy ワーカーによる取得）：他の Export の資源を求めるには「To claim another exported API, you must include its identityHash」であり、利用者は `APIBinding` で個別に受理する。これには Export と `Binding` の形が要るので、本 ADR では扱わない。
- **Cedar のエンティティの先例と文法**（2026-11-21 確認、agy ワーカーによる取得）：cedar-access-control-for-k8s（ https://github.com/cedar-policy/cedar-access-control-for-k8s ）は `k8s::User`・`k8s::Group`・`k8s::Resource` と `k8s::Action::"get"` などを使う。Cedar の文法（ https://docs.cedarpolicy.com/ ）は `Entity ::= Path '::' STR` であり、ID は任意の文字列なので `Nayutar::Object::"secret/db-creds"` と書ける。
- **LKAL の `Ref`**（`../LKAL/value.go`、2026-11-21 確認）：`Ref` は `[]string` のセグメント列である。[[0022]] の根拠のとおり、引用符なしのセグメントは `[A-Za-z0-9_.-]` で、修飾つき kind と `<name>` はその範囲に収まる。
- **LKAL のレコードのキーは `/` も空文字列も持てる**（`../LKAL/json.go` の `members`、2026-11-21 確認）：`FromJSON` がキーで拒否するのは、`$` で始まるもの（`L205`）と重複したもの（`L201`）だけである。決定 3 の置き場所のキーの制限は、この自由さのもとで `sourcePath` を一意にするためのものである。設計レビューで、`{"spec":{"db/password":{"$ref":"secret/x"}}}` が受理されることも確かめた。

- **手元での確認**（2026-11-21）：
  - `lake build` で、Lean モデルと 8 定理の証明（`sorry` なし）が通る。`#print axioms` で、8 定理が `propext`・`Classical.choice`・`Quot.sound` だけに依存することを確かめた。
  - `nayutar-drt refs` との DRT が、4 つのシードで各 1 万件一致する。7 種類の結果（受理と 5 種類の誤り、削除の受理と誤り）のすべてに到達し、わざと壊した 11 種の実装をどれも検出する。
  - ストア結合の試験は、インメモリ実装と 3 メンバーの etcd v3.6.16 の両方で通る（`-race` を含む）。ここには G0 の負の試験（キーをまねた表記、未許可の kind、Cedar が拒否したときの全体の巻き戻し）、参照先の比較による競合、64 を超える索引のキーの走査による削除、別テナントの同名オブジェクトに解決しないこと、が含まれる。
  - 設計レビューと差分レビュー（いずれも別のエージェント）の指摘のうち、`sourcePath` の曖昧さ、保存済みの参照先の上限、Cedar の要求のテナント、設定のエンティティの親を、本 ADR と実装に取り込んだ。

## 検討した代替案

- **葉パスまで存在を確かめる**：参照の誤りを早く見つけられる。しかし参照先の `spec` の書き換えで既存の参照が指す先が消えても再検査はしないので、保証が書き込みの一瞬にしか及ばない。参照先の文書の形に参照元が縛られるため採らない。
- **`status` の `Ref` も検査して許す**：観測状態にも参照を書ける。しかしコントローラが `status` に `Ref` を書いて、[[0010]] の項目 7 の読み取りの範囲を自分で広げる経路になるため採らない。
- **値だけで追加を数える**：同じ `Ref` を別の欄に移しても検査しない。しかし認可の要求は `sourcePath` を含むので、別の欄への移動は別の要求である。値だけで数えると、ある欄で許された参照を、許されていない欄へ持ち込めるため採らない。
- **書き込みのたびにすべての `Ref` を検査する**：ポリシーの変更が既存の参照にも及ぶ。しかし [[0010]] は追加分の検査を決めており、ポリシーを狭めると関係の無い `labels` の編集まで失敗するため採らない。
- **存在を確かめてから認可する**（[[0010]] の項目の並び）：誤りが分かりやすい。しかし認可されない書き手が `notFound` と `denied` の差から名前の有無を探れるため採らない。
- **Cedar の標準どおり、誤ったポリシーを無視する**：他の Cedar の利用と同じ挙動になる。しかし書き損じた `forbid` が黙って効かなくなり、fail-closed にならないため採らない。
- **参照先の存在だけを `Txn` で比べる**（mod revision > 0）：参照先が更新されても競合しない。しかし認可に使った `labels` が確認から書き込みまでに変わっても通ってしまう。属性を渡さずに存在だけを見る形にすると、参照先の側のオプトインをポリシーで書けなくなるため採らない。
- **認可を interface だけにし、cedar-go を後で入れる**：依存が増えない。しかし [[0010]] が名指しした Cedar での評価が未検証のまま残るため採らない。
- **スキーマ表を `.lkal` で宣言する**：人が書く設定を LKAL で書く規則に合う。しかし表の保存の形をスキーマの ADR より先に固定することになるため採らない。表は Go の値として渡し、形はスキーマの ADR で決める。
- **宣言の無い場所の `Ref` を通す**：導入が楽になる。しかし宣言の漏れがそのまま越境の穴になるため採らない。
- **索引の値に `sourcePath` の一覧を持つ**：どの欄から参照されているかを索引だけで分かる。しかし欄が変わるたびに索引の書き込みが増え、同じことは参照元の文書から読めるため採らない。
- **出現ごとに索引のキーを持つ**：欄ごとに引ける。しかし [[0006]] のキーの形にパスの区分が無いため採らない。
- **索引が空でないあいだ参照先の削除を止める**：参照が宙に浮かない。しかし [[0004]] の `Cmp` は 1 キーの比較だけで「範囲が空」を `Txn` で確かめられず、Kubernetes でも汎用の仕組みは凍結されている。[[0010]] は再評価をコントローラ側に残したため採らない。
- **参照先の数に上限を置かない／63 にする**：参照を多く書ける。しかし上限が無いと、更新のたびに参照先を少しずつ増やした結果、削除の `Txn` が上限を超えて消せなくなりうる。63 は etcd の上限の直下で、[[0013]] の所有権のキーを足す余地が無いため採らない。
- **ポリシーテンプレートでテナントの既定ポリシーを配る**：管理が楽になる。しかし cedar-go v1.9.3 にテンプレートが無いため採らない（[[0010]] のリスクのまま残る）。
- **参照先の側に `ReferenceGrant` 型の資源を置く**：[[0010]] で退けた。本 ADR は、参照先の `labels` を Cedar の属性に渡すことで、同じオプトインを認可の経路を増やさずに書けるようにする。

## 影響とトレードオフ

- **得るもの**：
  - テナントを越える `Ref`、未許可の kind、認可されない参照、存在しない参照先への参照を、書き込みの時点で拒否できる。拒否された書き込みは何も残さない。
  - 逆参照索引が、本体と同じ `Txn` で整合する。
  - 参照先の属性の有無で判定を変えないポリシーのもとでは、認可されない書き手に、テナントの中の名前の有無が漏れない。
  - 検査の性質が Lean の定理になり、Go の核が DRT でそれに結ばれる。
- **失うもの**：
  - 参照先より先に参照を書くこと、`status` に参照を書くこと、1 つのオブジェクトから 32 を超えるオブジェクトを参照することはできない。
  - `Objects` の `Create` と `Update` の引数に principal が増える。
  - 葉パスが参照先にあるかは確かめない。
  - 参照先が頻繁に更新されると、参照を追加する書き込みが競合で返りやすくなる。
- **引き受けるリスク**：
  - 追加でない `Ref` は検査し直さない。ポリシーの変更、参照先の削除、同じ名前での作り直しのあとも、既存の `Ref` は残り、作り直した別のオブジェクトを指しうる。索引は参照先の `uid` を記録しない。
  - principal は呼び出し側を信じる。認証は API サーバを決める ADR の範囲である。
  - ポリシー集合は設定で渡すだけで、テナントごとの保存と管理は無い。cedar-go にテンプレートが無いので、テナントの既定ポリシーの管理負担は [[0010]] のリスクのまま残る。
  - 評価の誤りを拒否として扱うので、属性を `has` で確かめずに引く広い範囲のポリシーは、属性を持たない要求をすべて拒否する。存在しない参照先には属性が無い。
  - 参照先の `labels` が認可の属性になるが、ラベルの文法はまだ決めていない（[[0025]]）。
  - 素のテナントビューとクラスタ全体の `store.Store` を通る書き込みは、検査も索引も通らない（[[0025]] と同じ）。そこで書かれた索引のキーや、そこで消された本体の索引のキーは残り、同じ名前で作り直したオブジェクトに引き継がれうる。
  - 読めない値を消す削除は、テナントの `ref/` を走査するので、索引が大きいと重い。
  - `Objects` を通らずに書かれ、段 1 に当たる文書（32 を超える参照先を持つものを含む）は、書き換えられない。削除して作り直す。
  - 置き場所のキーに `/` や空文字列を使う文書は、`spec` に `Ref` を持てない。
  - `Binding` を決める ADR は、Export された型への参照に、今の `&<修飾つき kind>/<name>` の意味を変えない表記を選ぶ必要がある。今の `Ref` はどれも `o/` のオブジェクトに解決する。
  - エラーで返った `Txn` は結果不明である（[[0020]]）。
  - 定理が述べるのはモデルである。Cedar の評価はモデルの外にあり、cedar-go の試験に頼る。
  - `Binding` と項目 7 が無いあいだ、Export された型への参照は表せない（修飾つき kind に identityHash が無い）。
- **今後の検証ゲート**：[[0010]] と [[0006]] が G0 に置いた `Ref` の負の試験（越境の表記、未許可の kind、Cedar が拒否したときの全体の巻き戻し）は、本 ADR のストア結合の試験がインメモリ実装と 3 メンバーの etcd で担う。G2 で NDSS 2026 の 2 つの攻撃類型を翻案した攻撃がすべて拒否されることを確かめる。Export と `Binding` を決める ADR で、identityHash つきの解決とコントローラの読み取りの制限を足す。
