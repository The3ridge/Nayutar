# 0034: 既定拒否ポリシーの実データプレーン上の穴を、入口ブリッジへの送信元束縛・ブリッジ族への写像・ホスト入力ガードで塞ぐ

## コンテキスト

[[0033]] は、テナント別ブリッジと `table inet nayutar` の `chain forward`（`policy drop`）で [[0016]] の既定拒否を実現し、宣言的評価器 `evaluate` とコンパイル済みチェイン `evalNft (compileNft cp)` の全パケット一致を Lean 4 で証明した。しかし証明が扱うのは「`forward` チェインに届いたパケットが、送信元アドレスどおりのテナントから来ている」場合だけである。実カーネルで実測すると、この前提の外に次の穴があった（2026-11-24、Linux 7.0、`nft` 1.1.6、非特権ユーザー名前空間の中に CNI と同じ形の構成を組んで確認）。

- **送信元の詐称**：`forward` チェインはテナントを `ip saddr` / `ip6 saddr` だけで判定する。テナント alpha の netns がテナント beta のアドレスを送信元にすると、beta→gamma だけに許可した UDP が gamma に届いた。containerd の既定 spec はコンテナに `CAP_NET_RAW` を与える。
- **同一ブリッジ内の L2 転送**：同じテナントのコンテナは同じブリッジにつながるので、`bridge-nf-call-iptables=0` ではパケットが `inet forward` を通らない。`intraTenant = .deny` でルールが無くても ping が届いた。同じ sysctl が 1 だと遮断されるので、[[0033]] が依存しないと決めた `br_netfilter` の状態で結果が変わる。
- **ホスト宛の通信**：コンテナからホスト自身のアドレス（他テナントのブリッジのゲートウェイアドレスを含む）への通信は `input` フックを通り、`forward` だけのテーブルでは遮断されない。
- **設定の組み合わせ**：`unit.tenant` を指定して `netpol` を省くと、テナント別ブリッジとゲートウェイで IP 転送が有効になるのにテーブルが置かれず、既定許可になる。`unit.tenant` と明示した `cni.bridge` の組み合わせで他テナントのブリッジにつなげられる。テナントを持たない unit のサブネットはポリシーの CIDR と照合されない。
- **`networkpolicy` kind の `spec.cidrs`**：テナントが自分の CIDR を宣言できる形になっており、[[0033]] 決定 1 の「CIDR を割り当てる」と食い違う。

満たすべき条件は 3 つある。[[0033]] の保護定理の主張（ユーザーが所有する）を変えないこと、`br_netfilter` を読み込ませないこと、ホスト上の他のブリッジの L2 転送や他のテーブルに干渉しないこと。

## 決定

1. **送信元を入口ブリッジへ束縛するガードチェイン `guard_forward` を `table inet nayutar` に置く。**
   - `type filter hook forward priority -10; policy accept;` とし、モデル化された `forward`（priority 0）より先に評価させる。
   - テナント T（ブリッジ `nbr-<T>`）ごと、アドレス族ごとに 2 規則を出す。`iifname "nbr-<T>"` から来て送信元が T の CIDR に無いものを `drop` し、送信元が T の CIDR にあるのに `iifname` が `nbr-<T>` でないものを `drop` する。T がその族の CIDR を持たないときは、`nbr-<T>` から来たその族のパケットを `drop` する。
   - これで `forward` チェインに届くパケットは「送信元アドレスが属するテナントのブリッジから入ったもの」に限られ、[[0033]] の定理の暗黙の前提が実カーネルで成り立つ。
   - 宛先も束縛する。宛先が T の CIDR にあるのに出口（`oifname`）が `nbr-<T>` でないものを `drop` する。
   - 束に無いテナントのブリッジを通さない。`nbr-` で始まるのに束のどのテナントのブリッジでもないインターフェースから入るもの、そこへ出るものを `drop` する。束から外したテナントのコンテナが残っていても、テナント外の送信元として振る舞えない。

2. **`intraTenant = .deny` のテナントがあるときだけ、同じコンパイル結果をブリッジ族 `table bridge nayutar` にも写す。**
   - `chain forward`（`type filter hook forward priority 0; policy accept;`）の先頭で、`.deny` のテナントのブリッジ以外（`meta ibrname`）を `accept` して対象を絞る。続けて ARP と IPv6 近隣探索（NS・NA）を `accept` し、ルータ広告とルータ要請（RA・RS）と、IPv4・IPv6 以外の EtherType を `drop` する。ホスト自身が出すフレームはブリッジ族の `forward` を通らないので、コンテナ同士が RA・RS を転送し合う正当な用途は無い。
   - 続けて、`.deny` のテナント T ごと、アドレス族ごとに、`nbr-<T>` の中を転送されるフレームの送信元と宛先を T の CIDR に束縛する（どちらかが外れていれば `drop`。T がその族の CIDR を持たないときはその族を `drop`）。同じブリッジの中で届く先は必ず T のコンテナなので、IP ヘッダが T の外を指すフレームは詐称か、近隣キャッシュを汚染して横取りした通信である。この束縛は `ct state` の規則より前に置く。経路を通った接続の conntrack の記録を、ブリッジ内の偽の応答が「確立済み」として使えないようにするためである。
   - その後ろに、`inet` 側の `forward` と同じ規則列（`ct state`、送信検査への `jump`、受信検査への `jump`）と同じテナントチェインを、同じ `NftTable` から機械的に出力する。末尾は無条件 `drop` とする。ポリシーを 2 か所に書くのではなく、1 つのコンパイル結果を 2 つの族へ出力する。
   - `.deny` のテナントが無いときは `table bridge nayutar` を定義しない。どちらの場合も、同じ `nft -f -` バッチの中で `table bridge nayutar` → `delete table bridge nayutar` を先に出し、古い定義を残さない。撤去のバッチも両方のテーブルを消す。
   - ブリッジ族の `ct state` はカーネルの `nf_conntrack_bridge` を要する。無い環境ではバッチの適用が失敗し、`lk-node` はコンテナを起動しない（fail-closed）。

3. **ホスト入力ガード `guard_input` を `table inet nayutar` に置く。**
   - `type filter hook input priority 0; policy accept;` とし、`iifname "nbr-*"` から来たものだけを対象にする。最初に束に無い `nbr-*` ブリッジを `drop` する（テナントが 0 個なら `iifname "nbr-*" drop` のみで終了し、束から外したテナントの残存コンテナが近隣探索や `ct state` に到達する経路を閉じる）。既知のブリッジについては `ct state { established, related }` と ICMPv6 の近隣探索（NS・NA・RS）を `accept` し、echo-request は「`nbr-<T>` から来て、宛先が T の CIDR にある」ものだけを `accept` し、残りを `drop` する。コンテナが ping できるホストのアドレスは、自分のテナントのゲートウェイだけになる。
   - `ct state` の規則より前に、送信元を束縛する。`nbr-<T>` から来て送信元が T の CIDR に無いもの（T がその族の CIDR を持たないときはその族すべて）を `drop` する。送信元が T の CIDR にあるのに、`nbr-<T>` でもループバックでもないインターフェースから来たものも `drop` する。束縛が無いと、コンテナが他テナントのアドレスを送信元にして自分のゲートウェイへ echo を打ち、ホストの応答を他テナントへ反射させられる。ホストが始めた通信への偽の応答も届く。近隣探索はリンクローカルや未指定の送信元を使うので、既知のテナントブリッジに限って束縛より前に `accept` する。
   - テナントのブリッジ以外から来るホスト宛の通信には、上の「テナントの送信元を名乗るもの」を除いて触れない。ループバックを除くのは、ホストが自分のゲートウェイアドレスと話す通信がループバックを通るからである。

4. **`lk-node` の設定を fail-closed にする。**
   - `unit.tenant` を指定したら `netpol` を必須にする。
   - `unit.tenant` を指定したときの明示的な `cni.bridge` は、そのテナントのブリッジ名と一致するときだけ受け付ける（[[0033]] 決定 1 の「`cni.bridge` 未明示時」を狭める）。
   - テナントを持たない unit は、`nbr-` で始まるブリッジを使えない。`netpol` があるときは、そのサブネットがどのテナントの CIDR とも重ならないことを検査する。

5. **配備前検査を `Enforcer` とスキーマ復号の境界に置く。**
   - テナントの CIDR に全域（`/0`）と IPv4 射影 IPv6（`::ffff:0:0/96` の内側）を認めない。束の中でブリッジ名が衝突するテナントの組を認めない。
   - Lean の `compile` は変えない。この検査は Lean モデルの外にあり、通った束だけが `compile` に渡る。
   - `nft` の実行ファイルの検査（[[0033]] 決定 3）を、実行ファイルを置くディレクトリからルートまでの各ディレクトリに広げる。どれも root が所有し、グループとその他に書き込みを許さないことを求める。

6. **`net.nayutar/networkpolicy` kind から `spec.cidrs` を外す。**
   - CIDR の割り当てはノードの運用者が書く束（`netpol.schema.lkal`）だけが持つ。kind が運ぶのは `intraTenant` と許可ルールだけにする。
   - kind のオブジェクトを束へ統合する規則（1 テナントに複数あるときの扱いを含む）は、コントローラの後続 ADR で決める。

7. **次のものは、この ADR では扱わない。**
   - 確立済みの接続：`ct state established` を先頭で `accept` し、適用時に conntrack を消さない。許可を取り消しても既存の接続は続く。
   - ポリシー更新の契機：適用は `lk-node` の起動時だけである。
   - 複数ノード：決定 1 の束縛は、テナントのアドレスが自ノードのブリッジからだけ来る単一ノードを前提にする。ノード間の経路を足す ADR で、許す入口を広げる。
   - Lean によるガードの証明：`guard_forward`・`guard_input`・ブリッジ族の前置部は Lean モデルに入れず、実カーネルの試験で確かめる。
   - ARP と近隣探索の送信者の束縛：同じテナントのコンテナは、同じブリッジの中で互いの近隣キャッシュを汚染できる。`.deny` のテナントでは、決定 2 の束縛により、テナントの外へ向かう通信は横取りした先へ転送される前に `drop` される（通信の妨害は残る）。`.allow` のテナントにはブリッジ族のテーブルがかからないので、同じテナントのコンテナが、他のコンテナのテナント外向けの通信を横取りできる。テナントの中のコンテナ同士は互いを信頼する、という前提をここで引き受ける。MAC アドレスの束縛は後続の ADR で扱う。
   - テナントに属さない送信元と宛先のあいだの転送：[[0033]] のモデルは、送信元も宛先もテナントに属さないパケットを `drop` する。`netpol` を適用したノードでは、テナントを持たない unit の経路を通る通信は届かない。これを変えるのはモデルの変更であり、この ADR では扱わない。

8. **`br_netfilter` がブリッジ内のフレームを `inet` のフックへ流す状態では、ポリシーを適用しない。**
   - `net.bridge.bridge-nf-call-iptables` と `net.bridge.bridge-nf-call-ip6tables` が 0 であるか、存在しない（モジュールが読み込まれていない）ことを、`Enforcer` がポリシーを入れるバッチの前に毎回確かめる。1 なら適用を拒否し、`lk-node` はコンテナを起動しない（fail-closed）。
   - この sysctl が 1 だと、ブリッジ内の L2 フレームが `inet forward` の `policy drop` に当たる。`.allow` のテナントの中の IPv6（近隣探索が規則に一致しない）と、ホスト上の無関係なブリッジの L2 転送が止まる。規則の側で両方の状態に対応する方法は、`inet` 族からブリッジ内転送を確実に見分ける一致条件が無いので採らない。
   - 読み取りは `sim.Disk` を経由する。適用した後でモジュールが読み込まれる場合は検出しない（引き受けるリスク）。

## 根拠（調査結果・出典）

- **穴の実測**（2026-11-24、Linux 7.0、`nft` 1.1.6、`unshare -Urnm` の中）：
  - `RenderNft` の出力を適用した状態で、`intraTenant = .deny`・ルール無しのテナントの同一ブリッジ内 ping が届いた（`bridge-nf-call-iptables=0`）。
  - 同じ状態で、alpha の netns が beta のアドレスを送信元にした UDP が、beta→gamma の許可で gamma に届いた（`rp_filter=2`）。
  - コンテナから他テナントのブリッジ上のホストアドレスへの ping が届いた。
- **方式の実測**（同じ環境、手で書いた規則）：
  - 決定 1〜3 の形の規則を 1 つのバッチで適用できた。`nf_conntrack_bridge` は読み込まれていない状態から自動で読み込まれた。
  - `.deny` のテナントで、同一ブリッジ内の ping と未許可ポートの TCP が遮断され、egress と ingress の双方で許可した TCP 8080 が IPv4 と IPv6 の両方で届いた。IPv6 の近隣探索も成立した。
  - `.allow` のテナントの同一ブリッジ内 ping は届いた。詐称した送信元からの TCP と、他テナントのブリッジ上のホストアドレス宛の TCP は遮断され、自分のゲートウェイへの ping は届いた。
- **試作を実装した後のレビューで見つかった穴の実測**（同じ環境、`RenderNft` の出力。alpha が `.deny`、beta が `.allow`）：
  - 決定 2 の束縛が無い状態で、alpha のコンテナが beta のアドレスを送信元にした UDP が、beta→alpha の許可で同じブリッジの別のコンテナに届いた。
  - alpha のコンテナが beta と許可された通信をした後、同じブリッジの別のコンテナが beta を装った応答を送ると届いた（経路側の conntrack の記録をブリッジ側が確立済みと判定した）。
  - alpha のコンテナが偽の ARP 応答でゲートウェイの近隣エントリを書き換えると、beta 宛の通信がそのコンテナに届いた。
  - `bridge-nf-call-ip6tables=1` では、`.allow` のテナントのブリッジ内の IPv6 と、無関係なブリッジの L2 転送が止まった。`br_netfilter` が読み込まれていると、新しい netns でもこの sysctl の既定は 1 だった。
  - 決定 3 の echo が束縛されていない状態で、他テナントのゲートウェイアドレスへの ping が届いた。
  - 決定 3 の送信元の束縛が無い状態で、alpha のコンテナが beta のアドレスを送信元にして自分のゲートウェイへ打った echo の応答（alpha が選んだペイロードを運ぶ）が beta のコンテナに届いた。ホストが beta のコンテナへ送った UDP に対する、alpha からの偽の応答もホストのソケットに届いた。
- **実装の実測**（同じ環境、`core/netpol` の実カーネル試験 21 本がすべて通過）：
  - 上の 6 つがすべて遮断され、それぞれの対照（許可した通信、自分のゲートウェイへの ping、ホストが始めた通信への本物の応答）は届く。ホストが自分のゲートウェイアドレスとループバック経由で話す通信、近隣キャッシュを消した後の IPv6（リンクローカルの送信元による近隣探索）も通る。`.deny` のテナントの中で偽の RA を送っても、隣のコンテナに既定経路は作られない。
  - 経路上の送信元詐称、テナントに属さないインターフェースからのテナント送信元の注入、束に無い `nbr-*` ブリッジからの転送、テナント宛のパケットがテナント外の出口へ出る配送、CIDR を持たない族の転送が遮断される。
  - `.deny` のテナントで、遮断と明示許可が IPv4 と IPv6 の両方で期待どおりになる。無関係なブリッジ（`nbr-` で始まらない）の L2 転送は `table bridge nayutar` があっても届く。
  - 決定 8 の sysctl のどちらかが 1 なら適用が拒否され、0 に戻すと適用できる。
  - 各規則を消した変異版では対応する試験が落ちる。IPv4・IPv6 以外の EtherType の `drop`（末尾の無条件 `drop` でも落ちる）は描画結果の試験（`render_test.go`）で固定している。ブリッジ族の「CIDR を持たない族」の `drop`（IPv4 のみの `.deny` テナントと IPv6 を持つ別テナントが同居するとき、他テナントの写像チェインへすり抜けるのを防ぐ必須の規則）および `guard_input` の未知 `nbr-*` 遮断については、描画結果の試験に加え実カーネル試験 2 本（`TestNftablesBridgeBlocksMissingFamilySpoofingOtherTenant`・`TestNftablesInputUnknownTenantBridgeCannotEnterHostConversation`、計 23 本）と `core/ci_test.go` での全 3 ファイル監視を追加した（追加 2 本の実カーネル動作は `-tags nftables` のコンパイル・静的検査を手元で通し、実カーネル実行は CI の `netpol-nftables` で確かめる）。
  - CI の Ubuntu 24.04 が持つ `nft` 1.0.9 では実行していない。`iifname "nbr-*"` と、インターフェース名の匿名集合を使う。受理されるかは CI の `netpol-nftables` が確かめる。
- **一次資料**：
  - ブリッジ族の接続追跡は Linux 5.3 以降で使える（https://wiki.nftables.org/wiki-nftables/index.php/Bridge_filtering ）。
  - `nft -f` は入力全体を 1 つのトランザクションで適用する（https://wiki.nftables.org/wiki-nftables/index.php/Atomic_rule_replacement ）。複数のテーブルを 1 つのバッチに入れても同じである。
  - `meta ibrname`・`iifname`・`ether type`・`icmpv6 type` の構文は `nft(8)`（https://www.netfilter.org/projects/nftables/manpage.html ）に従い、上の実測で受理を確かめた。
  - CNI `bridge` の `portIsolation` は、隔離ポート同士のブリッジ内 L2 直接通信を遮断する（https://www.cni.dev/plugins/current/main/bridge/ 。同一サブネット通信をゲートウェイ経由へ折り返すには代理 ARP・代理 NDP が別途要る）。代替案の評価に使った。
  - containerd の既定 spec が与える capability の一覧に `CAP_NET_RAW` がある（https://github.com/containerd/containerd/blob/main/pkg/oci/spec.go ）。

## 検討した代替案

- **入口インターフェースを Lean の `Packet` に入れ、束縛もモデル化する**：ガードまで証明の対象にできる。しかし `cross_tenant_requires_mutual_allow` などの主張の意味が変わり、ユーザーが所有する主張の書き換えが要る。まず実カーネルで穴を塞ぎ、モデル化は主張の変更として別に扱う。
- **CNI の `portIsolation` と代理 ARP・代理 NDP で、同一テナント内も L3 に通す**：ポリシーのテーブルが 1 つで済む。しかしブリッジごとの sysctl とアドレスごとの代理近隣エントリをノードが管理することになり、ポリシーを切り替えても既存のポートの隔離が変わらない。同じバッチで原子的に切り替わる写像を採る。
- **`rp_filter=1`（厳密）に頼る**：規則を足さずに済む。しかしホスト全体の sysctl であり、IPv6 には同じ仕組みが無い。
- **同一ノード内の `.deny` を対象外と明記する**：実装は要らない。しかし [[0033]] 決定 2 と定理が述べる意味論を、実データプレーンが満たさないままになる。
- **`table bridge` を常に置く**：場合分けが減る。しかし `.deny` を使わない構成にも `nf_conntrack_bridge` への依存とブリッジ内転送の接続追跡を負わせる。

[[0033]] は「単一共有ブリッジのまま `table bridge` と `table inet` を二重管理する」案を採らなかった。本決定はテナント別ブリッジを保ったまま、`.deny` のテナントのブリッジに限って、同じコンパイル結果を機械的に写す。ポリシーを 2 つ書き分けることはしない。

## 影響とトレードオフ

- **得るもの**：送信元の詐称（経路上とブリッジ内の両方）・同一ブリッジ内の L2 転送・ホスト宛の通信・設定の組み合わせに対して、[[0016]] の既定拒否が実カーネルで成り立つ。結果が変わる `br_netfilter` の状態では適用そのものを拒否する。保護定理の主張は変えない。
- **失うもの**：`.deny` を使う構成は `nf_conntrack_bridge` を要し、そのテナントのブリッジ内転送に接続追跡がかかる。`unit.tenant` と任意のブリッジ名の組み合わせは使えなくなる。コンテナからホストのサービスへは、自分のゲートウェイへの ping を除いて届かなくなる。`br_netfilter` を読み込んで sysctl を 1 にする他のソフトウェア（Docker や kube-proxy の既定の構成）と同じノードでは、sysctl を 0 にしない限り `lk-node` が起動しない。
- **引き受けるリスク**：ガードとブリッジ族の前置部は Lean の証明の外にあり、正しさは実カーネルの試験に頼る。CI の実行環境に `nf_conntrack_bridge` が無いと、`.deny` の試験が失敗する。決定 8 の検査は適用の時点だけなので、その後に `br_netfilter` が読み込まれると、決定 8 に書いた通信の停止が起きる（遮断が緩む方向ではない）。
- **今後の検証ゲート**：`nftables_linux_test.go`・`nftables_binding_linux_test.go`・`nftables_input_linux_test.go` の実カーネル試験 23 本（`.deny` の遮断と明示許可、経路上とブリッジ内の送信元詐称、`.deny` ブリッジ内の未割当アドレス族詐称、偽の応答、ARP 汚染による横取り、ホスト入力と未知 `nbr-*` 遮断、束に無いブリッジ、配送の束縛、決定 8 の拒否）を `core/ci_test.go` で監視し、CI の `netpol-nftables` で毎回実行する。複数ノード化とコントローラの ADR で、決定 6・7 の残りを扱う。
