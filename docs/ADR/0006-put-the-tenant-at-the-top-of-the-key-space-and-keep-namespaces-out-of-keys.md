# 0006: テナントをキー空間の最上位に置き、namespace をキー構造に含めない

## コンテキスト

[[0004]] のストア契約はバイト列キーに対するプレフィックス範囲走査（`Range`・`Watch`）を基礎としているため、キー空間の階層構造がそのまま分離境界・権限検査境界・将来的な物理シャーディング単位を決める。

Kubernetes では `namespace` が「名前の衝突を防ぐ命名単位」と「アクセス制御や分離の単位」を兼ねており、両者の結合がクロスネームスペース参照やクラスタスコープ参照を悪用する攻撃面になってきた。また [[0005]] の G2 以降でテナントごとに物理ストアを切り出す際、1 テナントに関連するすべてのキーを単一プレフィックスで捕捉できる構造が求められる。

## 決定

1. ストアのキー空間を次の構造に固定し、テナント識別子を最上位キー `/t/<tenant>/` とする。
2. `namespace` に相当する階層はキー構造に含めず、オブジェクト名内部の命名階層（または属性）として扱う。
3. システム共通の管理キーは `/sys/` 配下に、外部へエクスポートされたスキーマは `/x/<identityHash>/` 配下に配置する。

```
/t/<tenant>/o/<group>/<kind>/<name>     本体
/t/<tenant>/own/<group>/<kind>/<name>   所有権（葉パス→Actor）
/t/<tenant>/ref/<tKind>/<tName>/<sKind>/<sName>  逆参照索引
/t/<tenant>/bind/<identityHash>         Binding
/x/<identityHash>/schema/<version>      Export されたスキーマ
/sys/tenants/<tenant>
```

## 根拠（調査結果・出典）

- 内部不変条件：オブジェクト本体（`/o/`）・葉パス所有権（[[0013]] の `/own/`）・逆参照索引（[[0010]] の `/ref/`）・Binding（`/bind/`）をすべて `/t/<tenant>/` の下に集約することで、1 つのプレフィックス範囲だけでテナントの全状態を走査・watch・別ストアへ一括移設できる。またオブジェクト参照をテナント内相対名に閉じることで、名前解決と分離境界が一致する。
- Kubernetes Operator の越境参照脆弱性調査（NDSS 2026 "Breaking the Bulkhead", https://www.ndss-symposium.org/ndss-paper/breaking-the-bulkhead-demystifying-cross-namespace-reference-vulnerabilities-in-kubernetes-operators/ および https://arxiv.org/abs/2507.03387 ）：Go 製 Operator 2,268 件のうち 318 件（14% 超）が潜在的に脆弱で、8 件が確認され CVE 7 件が発行されたこと、攻撃戦略が「安全でないクラスタスコープ参照の悪用」と「安全でないクロスネームスペース参照の悪用」の 2 類型であることを確認した。隔離単位（テナント）と命名単位を分離することで、命名階層を跨ぐ参照が権限境界を越える構造を排する。
- APIExport / APIBinding モデル（kcp, https://docs.kcp.io/kcp/main/concepts/apis/exporting-apis/ ）：`apis.kcp.io/v1alpha2` において Export ごとに秘密の identity key と公開可能な `identityHash` を持つ設計を確認した。`/x/<identityHash>/` の公開スキーマと `/t/<tenant>/bind/<identityHash>` の束縛キーはこの分離に対応する。

## 検討した代替案

- **Kubernetes 型の `/registry/<resource>/<namespace>/<name>` 構造にする**：リソース種別が最上位になるため、1 テナントの全データを単一プレフィックスとして別ストアへ移設できず、[[0005]] の G2 シャーディングと衝突するため採らない。
- **種別（kind）優先のレイアウト（`/o/<kind>/<tenant>/<name>` 等）にする**：全テナント横断の型別検索には有利だが、テナント単位のプレフィックス watch・アクセス制御境界・一括移行が困難になるため採らない。
- **最初から接頭辞を持たずテナントごとに別ストアを割り当てる**：キー自体は単純になるが、G0〜G1 で多数テナントを単一クラスタで扱う際の管理・接続コストが過大になるため採らない（[[0005]]）。
- **テナント配下に namespace セグメントを設ける（`/t/<tenant>/ns/<namespace>/...`）**：namespace が再びパス構造に固定されると、namespace を跨ぐ参照の制御やクラスタスコープとの二重構造（NDSS 2026 で突かれた攻撃面）を招きやすく、オブジェクト名の命名階層だけで足りるため採らない。

## 影響とトレードオフ

- **得るもの**：隔離単位（`/t/<tenant>/`）と命名単位の分離により、越境参照の防止とテナント単位のストア分割・移行がキー構造レベルで成立する。[[0007]] のテナント×型別キャッシュとも自然に整合する。
- **失うもの**：全テナント横断で特定 kind だけを単一プレフィックスで `Range`・`Watch` する操作はできず、テナント単位の走査または `/sys/` での集約が必要になる。Kubernetes マニフェスト取り込み時には `namespace` をテナントまたは名前階層へ写像する変換が要る。
- **引き受けるリスク**：単一テナント内に極端に多くのオブジェクトが集中した場合、`/t/<tenant>/` より細かいプレフィックス単位への分割ができなくなる。また `/x/<identityHash>/` や `/sys/` の境界制御に誤りがあるとテナント分離を破る経路になり得る。
- **今後の検証ゲート**：G0 で越境 Ref の否定試験を検証し、G2（模擬 50,000 ノード・1,000 テナント）で NDSS 2026 の 2 攻撃類型を翻案した越境攻撃テストの全件拒否、およびテナント単位シャード化後の watch p99 遅延定数性（10,000 ノード時の 1.2 倍以内・p99 1 秒以内を初期値）を検証する。分割しても遅延が線形に増える場合は、テナント最上位とする本設計を見直す。
