# 0001: 動かさない前提の上で Kubernetes の本格的な代替を目指す

## コンテキスト

Nayutar は、個人と AI コーディングエージェントで Kubernetes の本格的な代替となるオーケストレータを作るプロジェクトである。着手前の調査（`poc.md`、2026-11-16）は、AI で実装が安くなることだけでは代替は成立せず、正解を機械判定できるオラクル（Kubernetes 本体・適合性テスト・決定論的シミュレーション・活性証明）を中心に据えた設計にして初めて技術面が個人＋AI の射程に入る、と結論づけた。最大の短所は技術ではなく、Operator エコシステムの引力・本番運用の経験・統治と信頼であり、ここは AI ではほとんど安くならない。

以後の設計判断（ストア・拡張モデル・互換層・コントローラ SDK など）は、どれも「何を目標にし、何を変えないか」に依存する。この前提を ADR として固定しておかないと、個々の決定が規模を縮めて「小さくて使われるもの」へ流れたり、人間が書く面に YAML が戻ったりしても、それが前提からの逸脱だと判定できない。

## 決定

Nayutar は次の前提を動かさない。前提を変えるときは、この ADR を `supersedes` する新しい ADR で行う。

1. **目標は Kubernetes の本格的な代替とする。** 「小さくて使われるもの」は目標にしない。
2. **宣言の基盤は LKAL とする。** LKAL 側の変更（Schema、Diff/Patch、順序付きレコード集合など）は許容する。所有権と apply の中核には kisage の葉パス所有権モデルを使う。
3. **JSON は使ってよい。人間が書く面に YAML は使わない。** YAML は取り込み入力（Helm / KRM / Compose など）としてのみ扱う。
4. **OCI・CNI・CSI・containerd などの既存資産を活かす。** データプレーンを自前で作り直さない。
5. **Kubernetes のつらさは引き受けない。** Certified Kubernetes は名乗らず、API 互換はワークロード部分互換の取り込み層に限る。
6. **開発は個人＋AI コーディングエージェントで行う。** そのため、品質は機械判定できるオラクルで外から確かめられる形にする。
7. **段階はすべて検証ゲートとして定義し、どの段階も製品として完結させない。** ゲート G0〜G4 の内容は `poc.md` §10.3 を出発点とし、個々のゲートの合格条件は別の ADR で定める。

前提 3 の「人間が書く面」は、Nayutar が利用者に提供する宣言・設定・API の面を指す。開発用の外部ツールが要求する YAML（`docdag.yaml`、ADR の frontmatter、GitHub Actions のワークフロー）はこの対象外とする。

## 根拠（調査結果・出典）

- `poc.md` §1：前提 1〜6 と「段階は検証ゲートとして定義する」は、調査の前にユーザーが指定した動かさない前提である。
- `poc.md` §2：AI による大規模実装の公開事例（C コンパイラ、形式証明）は、いずれも GCC やテストというオラクルがあったから成立した。前提 6 と 7 はこの観察に従う。
- `poc.md` §5：API 互換を持つと、認定のための適合性テスト実行、年 1 回以上の最新版提供義務、パッチ意味論・グローバル CRD・追従負担が戻る（CNCF Certified Kubernetes の要件）。前提 5 はこれを避けるための線引きである。
- `poc.md` §7：「宣言・差分・所有権は LKAL、API ワイヤは LKAL-JSON、外部標準の境界は plain JSON」という層の分担は数千ノード規模でも維持でき、高頻度経路にはバイナリ表現（LKAL-CBOR）を足せばよい。kisage の葉パス所有権は SSA の managedFields と同じ問題を解いている。前提 2 と 3 はこの分担に従う。
- `poc.md` §10.3・§10.4：ゲートごとに最初に検証する仮説と、失敗の兆候（watch 遅延の線形増加、検証の負債、AI 由来の回帰など）を定めている。前提 7 はこれを進行管理の単位にする。

## 検討した代替案

- **規模を絞った「小さくて使われる」オーケストレータを目標にする**：Nomad や Swarm に近い位置づけになり、成立条件は軽くなる。しかし目標そのものを変えることになり、ユーザー指定の前提に反するため採らない。
- **Certified Kubernetes 互換を目標にする**：既存の Operator やツールがそのまま動く可能性がある。一方で年 1 回以上の追従義務とパッチ意味論・グローバル CRD が戻り、「つらさを引き受けない」前提と両立しないため採らない。互換はワークロード部分互換の取り込み層と差分オラクルに限る。
- **人間が書く面にも YAML を許す**：既存資産との親和性は高い。しかし型が構文で決まらず、暗黙の型変換を含む YAML を宣言面に戻すと LKAL を基盤にする意味が薄れるため採らない。YAML は取り込み入力としてだけ扱う。
- **前提を ADR にせず README や調査メモに置く**：書く手間は小さい。しかし DocDag の `supersedes` で前提の変更履歴を追えず、後続 ADR から `depends-on` で参照できないため採らない。

## 影響とトレードオフ

- **得るもの**：後続の設計判断を「前提に合うか」で機械的に棄却できる。前提の変更は `supersedes` として `docdag diff` に現れる。
- **失うもの**：既存の Operator・CRD・Admission Webhook に依存する資産は、そのままでは動かない。移植経路（検証付き SDK への AI 支援移植）を用意するまで、これが最大の短所として残る。
- **引き受けるリスク**：状態ストアが最大の技術リスクであり、個人は大手と同じ資源を持たない。セキュリティ対応と継続性は個人の単一障害点になる。どちらも前提を変えずに、検証ゲートの合否で早期に検出する。
- **今後の検証ゲート**：最初に G0（形式仕様・決定論的シミュレータ・Kubernetes 差分ハーネス）の合格条件を ADR として定める。実装言語・ストア構成・拡張モデルなどの設計判断は、それぞれ別の ADR で、この ADR に `depends-on` して記録する。

## 関連ADR
