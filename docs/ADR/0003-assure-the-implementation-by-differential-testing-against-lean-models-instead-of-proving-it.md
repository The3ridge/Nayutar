# 0003: 実装自体は証明せず、Lean モデルとの差分試験で正しさを担保する

## コンテキスト

[[0002]] で中核の実装言語を Go、仕様と証明の言語を Lean 4 と定めた。残る問題は、Go の実装コードと Lean 4 の仕様・証明をどの方法で結びつけ、個人＋AI エージェント体制での検証負債を防ぐかである。

計画書（`docs/research/draft_20261117_001.md` §1・§2.1・§7.3）は当初検討していた「Anvil＋Verus で主要コントローラの実装レベルの活性（eventually stable reconciliation: ESR）まで証明する」方針を撤回した。ここでも VeruSAGE リーダーボードの最新数値（Opus 4.5 で高水準）は実装証明の障壁が下がったことを示すが、[[0002]] で Go 中核を選んだ以上、Go 実装へ実用的なプログラム論理で直接 ESR を証明する経路が未成熟である点を踏まえて接続方式を確定する必要がある。

## 決定

1. **Go の実装コード自体は形式証明しない。**
2. **ストア／watch、所有権／apply、パス写像で表せる変換のそれぞれに実行可能な Lean 4 モデルを作り、Go 実装と差分ランダムテスト（DRT）で突き合わせる。**
3. **ESR は Lean 4 上の抽象状態機械で証明し、Go コード上では証明しない。**
4. **Kubernetes v1.37 系（kind および kwok）を外部の差分オラクルとして用いる。**
5. **AI エージェントは Lean の証明本体を書いてよいが、定理の主張（statement）を変更してはならない。**
6. **Welder からは設計原則のみを取り込む。** 具体的には「コントローラは自身のスコープ内にしかリクエストを出さない」という rely-guarantee と、バージョン競合を避けるトランザクション抽象の 2 点とする。

## 根拠（調査結果・出典）

- **先行実証（kisage と Cedar）**：kisage（`https://github.com/Kaikei-e/kisage`）は Lean 4 で Plan 安全性定理 11 個（`sorry` 0）と 9 フィールドの `ProtocolInvariant` を持ち、1,728 件の列挙ケースで Lean と Go を比較する `kisage-drt` がすでに動いていることを確認した。ただし kisage では ESR 自体は未証明であり、`Kisage/Convergence.lean` が示すのは単一パス上の有限収束と候補 ESR ランク関数の定式化にとどまり、ESR 本体は kisage の ADR 0005 で Phase 5 に残されている。Cedar（`https://arxiv.org/abs/2407.01688`）も同様に、Lean モデル上の証明と別言語実装を DRT で結ぶ構成を採っている。
- **Anvil・Welder・VeruSAGE の位置づけ**：Anvil（`https://www.usenix.org/system/files/osdi24-sun-xudong.pdf`）は Verus 上でコントローラの ESR を証明し、Welder（`https://cathy-cai.page/pubs/welder26.pdf`、DOI `10.1145/3830418.3843868`）は ReplicaSet・Deployment・StatefulSet・RabbitMQ コントローラの合成が CORE（ESR＋要求中心の rely-guarantee）を満たすことを示した。一方 VeruSAGE リーダーボード（`https://raw.githubusercontent.com/microsoft/verus-proof-synthesis/main/leaderboard/data/verusage-bench-results.json`、2026-01-21 更新、元論文 `https://arxiv.org/abs/2512.18436`）では Opus 4.5 が Anvil Controller 課題 63 件中 52 件（82.5%）・全体 797/849（93.9%）を解いており、AI 証明の困難さだけを理由に実装証明を退けることはできない。それでも [[0002]] の Go 資産とツール安定性の判断を優先し、Welder からは上記 2 原則だけを設計に取り込む。
- **Go 直接検証の現状**：Perennial（`https://github.com/mit-pdos/perennial`）の `lean` ブランチは `iris-lean` 上の Lean 4 で goose 変換済み Go とクラッシュ意味論・妥当性定理を扱うが、クラッシュプログラム論理および分散プログラム論理が存在せず、実用 Go システム全体の検証事例は未確認である。Gobra（`https://github.com/viperproject/gobra/releases`）は v26.09 などの定期リリースを持つが、本プロジェクトへの適用可否は未確認である。
- **外部差分オラクルの版**：Kubernetes v1.37 は 2026-08-26 公開予定（`https://kubernetes.io/blog/2026/07/31/kubernetes-v1-37-sneak-peek/`）を経て 2026-09-08 時点で出荷済みと確認した（`https://kubernetes.io/blog/2026/09/08/kubernetes-v1-37-advancing-workload-aware-scheduling/`）。よって v1.37 系を基準オラクルとする。
- **定理保護と初期数値**：AI エージェントに定理の主張変更を許すと目標仕様を弱めて検証をすり抜ける余地が残る（`docs/research/draft_20261117_001.md` §7.5 項目 6）。G0 の DRT 各 1,000 ケース・kind 差分 30 シナリオ以上、PR 時 DRT 1,000・マージ後 10,000 などの件数はいずれも初期値とする（同 §7.4・§8.1）。

## 検討した代替案

- **Anvil＋Verus（Rust）で主要コントローラの実装レベル ESR まで証明する**：実装と証明の乖離が原理的に消える。しかし [[0002]] で選んだ Go 資産（LKAL・kisage）を全面的に作り直すことになり、週次でリリースされる Verus への追従負担も加わるため採らない。
- **Perennial や Gobra で Go 実装を直接検証する**：Go 実装のまま証明を持てる可能性がある。しかし Perennial の Lean 4 版はクラッシュプログラム論理と分散プログラム論理を欠き、Gobra も本プロジェクトでの有効性が未確認であるため、初期の基盤としては採らない。
- **形式モデルを作らず、Kubernetes 差分試験と通常のテストだけで担保する**：実装の手間は軽い。しかし所有権や watch の境界条件を有限の手書きテストで覆い切ることはできず、[[0001]] のオラクル中心設計が片肺になるため採らない。
- **Lean の定理の主張編集も AI エージェントに許可する**：仕様変更と証明を 1 タスクで回せる。しかし失敗する定理を書き換えて通す回帰を防げないため採らない。

## 影響とトレードオフ

- **得るもの**：実装と仕様を分離することで AI エージェントによる実装反復を速く保ちつつ、Lean モデル（安全性・ESR）と Kubernetes v1.37（外部挙動）の二重オラクルで正しさを検査できる。
- **失うもの**：Go 実装と Lean モデルの間の乖離（モデル化していない並行性やリソース枯渇）を定理としては排除できない。
- **引き受けるリスク**：DRT の生成器やシミュレーションの網羅不足によるバグ見逃し、および kind 差分の偽陽性による検証停止リスクを引き受ける。補完として [[0015]] の決定論的シミュレーションと履歴検査を併用する。
- **今後の検証ゲート**：G0 で Lean–Go DRT（ストア／watch・所有権 CAS 版各 1,000 ケース、初期値）、所有権の CAS 版プロトコルモデルの証明（範囲は [[0013]] で定める）、watch 不変条件 4 件（[[0007]]）、kind v1.37 差分 30 シナリオ以上（偽陽性 0 件、初期値）を検証する。次のいずれかが起きた場合は本決定を見直す：(1) Perennial の Lean 4 版がクラッシュプログラム論理・分散プログラム論理を備え、実用 Go システム全体の検証事例が確認されたとき、(2) DRT やシミュレーションが、実装レベルの証明があれば防げたバグを繰り返し見逃したとき。
