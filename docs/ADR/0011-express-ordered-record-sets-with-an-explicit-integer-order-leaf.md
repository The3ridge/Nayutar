# 0011: 順序付きレコード集合は文書内の明示的な整数 order 葉で表す

## コンテキスト

CNI のプラグイン列のように、各要素がラベル付きレコードでありながら適用順序を持つ設定が存在する。[[0001]] の前提 2 は「順序付きレコード集合など LKAL 側の変更を許容する」としていた。しかし LKAL の設計原則（`docs/PRINCIPLE.md`）および LKAL の ADR 0010 を確認したところ、LKAL は List を単一型スカラーのみに制限し、かつ `Equal` が Record のフィールド順を無視して外部スキーマに依存しない不変条件を採っている。この不変条件を壊さずに順序付きレコード集合を扱う表現を定める必要がある。

## 決定

[[0001]] 前提 2 が許容する LKAL 側の型拡張は行使せず、順序付きレコード集合を次の規約で表す。

1. LKAL に新しい型を追加せず、既存のラベル付きレコードの集合として記述する。
2. 各要素の順序は文書内に明示的な `Int` 型の葉（`order`）として書き、挿入時の再採番を避けるため疎な整数（10, 20, …）を初期値とする。
3. スキーマは検証のみを行い、対象集合内の各レコードに `order` 葉が存在することと、集合内で `order` 値が重複しないことを検査する。`Equal`・構文解析・`Format` は変更しない。
4. 順序に基づく整列は、順序を必要とする消費者側（たとえば CNI 呼び出し前にプラグイン配列を組み立てる処理）が `order` 葉を読んで行う。
5. `.../order` も他の葉と同じ葉パスであり、並び順の変更には [[0013]] に従う所有者が付く。

```lkal
plugins {
  plugin "bridge" { order = 10, type = "bridge", bridge = "lk0" }
  plugin "portmap" { order = 20, type = "portmap" }
}
```

## 根拠（調査結果・出典）

- LKAL（`https://github.com/Kaikei-e/LKAL`）の `docs/PRINCIPLE.md`（§6・Out of Scope・Checklist、2026-11-17 確認）：データモデルは 9 型にとどめ、List は単一型スカラーのみ（L204）、`Equal(a, b)` は文書テキストのみから決まり Record のフィールド順を無視し、外部スキーマ（v0.2 予定）は値検証だけを担いパース・フォーマット・`Equal` を変えてはならないことを確認した。
- LKAL の ADR 0010（accepted）：Collection を Record に統合して 9 型を維持し、`lkal.Equal` をスキーマ非依存の純粋関数に保つために「スキーマで宣言する順序付き集合」の構想を削除したことを確認した。
- `docs/research/draft_20261117_001.md` §1（項目 4）・§2.1（項目 3）・§6.2：型追加ではなくデータ上の `order` 葉とスキーマ検証で扱う整理に基づく。なお同節の LKAL 例は構文不備を修正し、`lkal check` を通る構文で記載した。

## 検討した代替案

- **LKAL に順序付きレコード集合の専用型を追加する**：[[0001]] 前提 2 の範囲では可能だが、9 型モデル・`Equal`・正規形・LKAL-JSON・葉パス所有権のすべてに変更が波及し、LKAL の ADR 0010 が守った原則と衝突するため採らない。
- **スキーマで順序付き集合を宣言して `Equal` や整形の順序を変える**：文書に `order` 葉を書かずに済む。しかし型と `Equal` をスキーマ非依存に保つ LKAL の原則に反し、LKAL の ADR 0010 で棄却されているため採らない。
- **ソース記述順（`Format` が保存する順）を順序として使う**：追加の葉が不要になる。しかし `Equal` は Record のフィールド順を無視するため記述順はデータモデルに属さず、JSON 往復（[[0012]]）や部分更新で保持を保証できないため採らない。
- **並び順を表す名前リスト（スカラー List）を別パスに持つ**：各レコード内に `order` を書かずに済む。しかし要素の定義と順序が 2 箇所に分離し、要素追加・削除時の不整合と List 全体書き換えによる所有権競合を招くため採らない。

## 影響とトレードオフ

- **得るもの**：LKAL の 9 型・`Equal`・`Format`・LKAL-JSON（[[0012]]）を変えずに順序付き集合を表現できる。また順序が文書内の `.../order` 葉というデータになるため、[[0013]] の葉パス所有権モデルで並び替えの所有者をそのまま追跡できる。
- **失うもの**：記述者は並び順を `order = 10` のように明示する必要があり、Kubernetes YAML の配列から取り込む際には `order` 値を機械的に付与する変換が必須になる。
- **引き受けるリスク**：疎な整数でも連続挿入を繰り返すと間隔が枯渇し再採番が必要になる場合がある。また LKAL スキーマ言語は未実装であり、集合内の `order` 一意性制約をどう記述するかは未確認である。
- **今後の検証ゲート**：G0 の変換・差分ハーネス（[[0003]]）で、配列形式の取り込みと消費者側ソートの往復性を性質ベース試験・差分試験で検証する。取り込み変換や実運用で一意性検証の表現力が不足した場合は、スキーマ仕様または本表現を再検討する。

## 関連ADR

- [[0001]]：本決定が前提とする。前提 2 で順序付きレコード集合などの LKAL 変更を許容していたが、本 ADR では言語変更を行わない選択をする。
- [[0003]]：本表現を含む変換の往復性を性質ベース試験・ファジングで検証する方針を定める。
- [[0012]]：本表現をそのまま LKAL-JSON / LKAL-CBOR のレコードとしてシリアライズする。
- [[0013]]：`.../order` 葉を通常の葉パスとして所有権管理するモデルを定める。
