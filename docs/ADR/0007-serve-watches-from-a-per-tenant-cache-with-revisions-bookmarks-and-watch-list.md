# 0007: リビジョン・ブックマーク・watch list を備えたテナント×型別キャッシュから読み取りと watch を配信する

## コンテキスト

[[0005]] により G0〜G1 は単一 etcd クラスタを全テナントで共有するため、読み取りや LIST、多数のクライアントによる watch を直接 etcd へ流すと合意ストアが飽和する。[[0006]] のキー構造によりデータはテナント×型ごとに独立しているため、API サーバ内にこの単位のメモリキャッシュを置けば負荷吸収とテナント間分離を両立できる。

同時に、キャッシュ経由でも最新状態の一貫読み取りを保証し、更新のない静かなプレフィックスでキャッシュが停止しない仕組み、および初期状態の大量 LIST に代わる watch list 配信の意味論を定める必要がある。

## 決定

1. API サーバ（`lk api`）は、**テナント×型ごと**にリングバッファと B-tree スナップショットからなる自作 watch キャッシュを保持し、読み取りと watch をキャッシュから配信する。
2. **一貫読み取り**：[[0004]] の `CurrentRev` を quorum 読み取りで取得し、キャッシュがそのリビジョンに追いつくまで最大 **3 秒**（初期値）待つ。更新のないプレフィックスでは [[0004]] の `RequestProgress` で進捗通知を要求してキャッシュを進め、タイムアウト時はストアへ直接フォールバックする。
3. **ブックマーク**：到達済みリビジョンを通知するブックマークを **60 秒**ごと（初期値）に送信する。
4. **watch list**：初期状態の取得を伴う watch では、現在状態を個別の追加イベントとして送った後、初期イベント終了を示すブックマークを送り、続けて差分イベントを配信する。
5. **範囲外リビジョンとコンパクション**：要求リビジョンがリングバッファ保持範囲より古い場合は **410** を返してクライアントに再取得（relist）させる。ストアの `Compact` は、全キャッシュが変更を受け取り終えたリビジョンまでに限って実行する。キャッシュが保持する最古リビジョンは境界にしない。変更の少ないキャッシュは決定 6 の件数に届かず、初期状態を読んだときのリビジョンを保持し続けるので、それを境界にするとコンパクションが進まなくなる。
6. **リングバッファ保持量**：`10,000 件または 150 秒のうち長い方` を `docs/research/draft_20261117_001.md` §5.2 に基づく初期値とする（Kubernetes の 75 秒とは異なる独自初期値であり、検証ゲートで調整する）。
7. **形式検証**：Lean 4 で「欠落なし・重複なし・順序保存・ブックマーク単調性」の 4 不変条件を証明し、Go 実装とは [[0003]] に基づく DRT と線形化可能性検査で結ぶ。

## 根拠（調査結果・出典）

- 内部不変条件：[[0004]] の単調増加リビジョン・`CurrentRev`・`RequestProgress` と [[0006]] のテナント×型プレフィックスを組み合わせ、欠落なし・重複なし・順序保存・ブックマーク単調性の 4 不変条件を保つことで、再接続時の取りこぼしや重複を防ぐ。
- KEP-2340 "Consistent reads from cache"（ https://github.com/kubernetes/enhancements/blob/master/keps/sig-api-machinery/2340-Consistent-reads-from-cache/README.md ）：API サーバが quorum 読み取りで現在リビジョンを取得し、watch キャッシュの追従を最大 3 秒待ってタイムアウト時に etcd の quorum 読み取りへフォールバックすること、および書込みがない区間でキャッシュを進めるため etcd の `RequestProgress` に依存することを確認した（v1.31 で Beta、v1.34 で GA）。必要な etcd の版は、KEP の本文が v3.4.25+ または v3.5.8+ とし、Kubernetes のブログ（ https://kubernetes.io/blog/2024/08/15/consistent-read-from-cache-beta/ ）が 3.4.31+ または 3.5.13+ とする。
- KEP-3157 watch-list（ https://github.com/kubernetes/enhancements/issues/3157 ）：`sendInitialEvents=true` により現在状態を合成 ADDED イベントとして送り、`k8s.io/initial-events-end: "true"` 注釈つき BOOKMARK の後に差分を送る設計を確認した（`kep.yaml` は v1.32 で Beta とし、v1.37 時点でも Beta）。
- Kubernetes watch キャッシュ実装・API 概念（ https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/apiserver/pkg/storage/cacher/cacher.go および https://kubernetes.io/docs/reference/using-api/api-concepts/ ）：範囲外 `resourceVersion` に `410 Gone`（"too old resource version"）を返すこと、ブックマーク間隔が 1 分であること、および循環バッファは 100〜102,400 イベントの範囲で動的に調整され最低 75 秒の履歴を保持することを確認した。よって `docs/research/draft_20261117_001.md` §5.2 の「10,000 件または 150 秒」は Kubernetes 由来の定数ではなく本設計の初期値である。
- コンパクション境界（ https://etcd.io/docs/v3.5/learning/api/ ）：コンパクション済みリビジョンを指定した watch は `compact_revision` を返して終了する。キャッシュの上流の watch がストアの履歴から読むのは、受け取り終えたリビジョンより後の変更だけである。保持範囲の中の読み取りと watch はキャッシュのメモリから返すので、ストアの履歴を使わない。そこで、全キャッシュが受け取り終えたリビジョンまでのみ `Compact` する規則を置く。

## 検討した代替案

- **キャッシュを置かず、すべての読み取り・watch をストアへ直接流す**：実装は単純だが、多数クライアントからの読み取り・watch 負荷が [[0005]] の単一 etcd クラスタに集中し、G1（10,000 ノード）に耐えられないため採らない。
- **watch list を使わず、従来の全件 LIST＋watch のみにする**：大きな状態の再取得時にメモリ使用量が急増するため、ストリーミングで初期状態と差分を連続配信できる watch list を採る。
- **etcd の watch ストリームをクライアントへ直接公開する**：[[0004]] のストア契約と [[0005]] の将来のストア差し替えがクライアントに露出し、テナント境界や認可・Ref フィルタの挿入も難しくなるため採らない。
- **テナントで分割せず単一のグローバルキャッシュにする**：全テナントのイベントが 1 本のリングバッファを奪い合い、1 テナントの大量更新で他テナントの履歴が押し流されて 410 が多発するため採らない。

## 影響とトレードオフ

- **得るもの**：読み取りと watch ファンアウトを API サーバのメモリで吸収しつつ一貫読み取りを保てる。テナント×型分離により他テナントの更新負荷から履歴保持を隔離できる。
- **失うもの**：API サーバがメモリ上のキャッシュ状態を持つため、メモリ使用量が増え、プロセス再起動時のキャッシュ構築や複数 API サーバ間での履歴保持差への対処が要る。
- **引き受けるリスク**：静かなプレフィックスでの `RequestProgress` 遅延や 3 秒タイムアウトが頻発するとストア直読みフォールバックが増え、etcd 負荷が戻る恐れがある。また固定初期値（10,000 件または 150 秒）が不適切だと 410 relist が多発する可能性がある。
- **今後の検証ゲート**：G0 で Lean 4 による 4 不変条件の証明、およびストア/watch の DRT 1,000 ケース以上と線形化可能性検査を検証する。G1（模擬 10,000 ノード）で watch p99 遅延 1 秒以内、ノードあたり制御面 CPU が 1,000 ノード時の 1.5 倍以内（いずれも初期値）を検証し、410 多発・フォールバック率悪化・遅延増加が見られた場合はリングバッファの動的調整方式を含めて見直す。
