# 0023: watch キャッシュを、永続 B-tree・閉じたリビジョン・プロセス内のコンパクション境界を持つライブラリとして実現する

## コンテキスト

[[0007]] は、テナント×型ごとのキャッシュから読み取りと watch を配信すると決めた。[[0007]] が決めたのは方式と初期値であり、次の点は決めていない。

- API サーバ（`lk api`）と値の封筒（[[0009]]）はまだ無い。キャッシュをどこに置き、「410」を何で表すか。
- B-tree のスナップショットを何で作るか。
- 保持量「10,000 件または 150 秒のうち長い方」に上限が無い。150 秒のうちに大量の更新が来ると、その全件を保持する。
- [[0004]] の `WatchStream` は、1 つのトランザクションの変更を 1 件ずつ流す。受け取った側は、あるリビジョンの変更をすべて受け取ったかどうかを、次のリビジョンの変更か進捗通知が届くまで判定できない。Kubernetes は 1 リビジョンで 1 オブジェクトしか変えないので、この問題を持たない。
- コンパクションの境界（全キャッシュが変更を受け取り終えたリビジョン）を、誰がどの範囲で集めるか。
- [[0007]] の 4 不変条件を、どのモデルの上の、どの主張として書くか。主張のファイルはユーザーの所有である（[[0017]]）。

## 決定

1. **ライブラリとして `core/store/watchcache` に置く。** HTTP の配信は作らない。範囲外リビジョンは誤り `ErrTooOld` で表し、HTTP の 410 への対応づけは API サーバを決める ADR に残す。値はバイト列のまま扱い、封筒を解釈しない。
2. **キャッシュは 3 層に分ける。**
   - `core/store/watchcache/btree`：永続（パスコピー）B-tree。標準ライブラリだけで自作する。更新は新しい木を返し、古い木は変わらない。スナップショットは木の値を持つだけで作れる。
   - 決定的な中核（状態機械）：ゴルーチン・時計・ストアを持たない。入力は初期状態、上流の変更、上流の進捗通知、時刻である。Lean モデルと 1 対 1 に対応させ、DRT はこの層を比べる。
   - 並行する外殻：上流の `Range` と `Watch` で中核を進め、読み取りの待ち合わせ、ストアへのフォールバック、ブックマークの周期、watch の配信を担う。
3. **「閉じたリビジョン」だけを読み取りとブックマークに使う。** キャッシュは、変更をすべて受け取ったと分かっている最大のリビジョン（閉じたリビジョン）を持つ。
   - リビジョン `r` の変更が届いたら、`r - 1` までが閉じる。進捗通知 `p` が届いたら、`p` までが閉じる。
   - 一貫読み取り、リビジョン指定の読み取り、スナップショット、watch list の初期状態、ブックマークは、閉じたリビジョンだけを見る。
   - watch の差分イベントは、届いたものから配信する。開いたリビジョンの変更も配信するので、watch の受け手がトランザクションの途中を見ることがある。これは [[0004]] の `WatchStream` を直接読む場合と同じである。
   - ブックマークは、開いたリビジョンが無く、その watch が受け取り済みの変更をすべて配信し終えたときにだけ送る。値は閉じたリビジョンである。
   - ブックマークの期限は 60 秒ごと（[[0007]] の初期値）に来る。期限が来た watch は、上流の進捗通知を 1 つ待ってから送る。通知が 3 秒届かなければ、そのときの閉じたリビジョンで送る。進捗の要求は、一貫読み取りの待ちと同じ 1 本の周期を、待つ者の全員で共有する。watch がストアを直接読むことは無い。
   - 契約に反する上流の入力（リビジョンの逆行、閉じたリビジョン以下の変更）を受けたら、中核はそれを拒否し、外殻は読み直す。
4. **一貫読み取りは次の手順で行う。** `CurrentRev` を読み、閉じたリビジョンがそこに達するまで最大 3 秒待つ。待つあいだ、上流の watch に `RequestProgress` を送る（契約は、追いつくまでの要求を黙って捨てる）。要求は 100 ミリ秒に 1 回までとし、直前の要求から 100 ミリ秒が過ぎていれば、待ちが始まったときにすぐ送る。達しなければ、ストアを直接読む。キャッシュがまだ初期状態を読み終えていないときも同じである。
5. **リビジョン指定の読み取りとページング。** 保持範囲の中のリビジョンは、そのリビジョンのスナップショットから返す。スナップショットは閉じたリビジョンごとに 1 つ持つ。保持範囲より古いリビジョンはストアに渡す。閉じたリビジョンより新しいリビジョンは 3 秒まで待ち、達しなければストアに渡す。
6. **watch の開始位置。** `fromRev` は [[0004]] と同じく、その値を含む。
   - `fromRev = 0` は、閉じたリビジョンの次から始める。
   - 保持範囲より古い `fromRev` は `ErrTooOld` で拒否する。
   - 閉じたリビジョンの次より新しい `fromRev` は 3 秒まで待ち、達しなければ `store.ErrFutureRev` で拒否する。
   - 配信が保持範囲に追い越された watch は `ErrTooOld` で終わる。キャッシュは watch ごとの待ち行列を持たず、各 watch はリングバッファ上の位置だけを持つ。
   - watch は、リングバッファから 1 度に 64 件までを取り出して送る。受け手が読まないあいだ、watch は送信で止まる。追い越しは、取り出した分を送り終えて次を取り出すときに検出する。
   - 上流の watch が終わり、キャッシュが読み直したとき、開いている watch はすべて `ErrTooOld` で終わる。
7. **watch list。** 初期状態つきの watch は、閉じたリビジョン `R` の状態をキー順の追加イベントとして送り、`R` を持つ初期イベント終了のブックマークを送り、続けて `R` より後の変更を送る。追加イベントのリビジョンは、そのキーの mod revision である。
8. **保持量。** 「10,000 件以上残り、かつ 150 秒より古い」リビジョンから捨てる。加えて、保持が **102,400 件**（初期値）を超えたら、150 秒に満たなくても古い方から捨てる。
   - 捨てる単位はリビジョンである。1 つのリビジョンの変更を途中で切らない。
   - 開いたリビジョンは捨てない。
   - 102,400 件は Kubernetes の上限と同じ値であり、[[0007]] には無い本 ADR の初期値である。
   - 件数と時間は設定で変えられる。
9. **コンパクションの境界は、閉じたリビジョンをプロセス内で集めて決める。** `Manager.Compact` は、準備のできた全キャッシュの閉じたリビジョンの最小値より先へコンパクションを進めない。
   - `Manager.Compact` は、まず各キャッシュに、頼まれたリビジョンまで追いつく時間を最大 3 秒与える。待つあいだ、キャッシュは決定 4 と同じ進捗要求を送る。変更の無いキャッシュも、進捗通知で閉じたリビジョンが進む。
   - 追いつかなかったキャッシュがあれば、その閉じたリビジョンまで下げて実行し、実行したリビジョンを返す。
   - キャッシュが保持する最古のリビジョンは境界にしない。保持範囲の中の読み取りと watch はメモリから返すので、ストアの履歴を使わない。ストアの履歴が要るのは、上流の watch がまだ受け取っていない変更だけである。
   - 境界が及ぶのは `Manager.Compact` を通るコンパクションだけである。ストアの `Compact` を直接呼ぶ者は止めない。
   - 初期状態を読み終えていないキャッシュは何も保持していないので、境界に入れず、待ちもしない。そのキャッシュは、読み込みがコンパクションに追い越されたら読み直す。
   - 複数の API サーバにまたがる境界の集約は作らない。API サーバを複数にする ADR で決める。
10. **キャッシュの単位。** `Manager` は、テナントと `(group, kind)` ごとに、本体のキー（`o/<group>/<kind>/`）のキャッシュを、最初に使われたときに作る。キーは [[0022]] のコーデックで組み立て、テナントビュー（[[0020]]）の上に置く。キャッシュが返すキーは、テナントの中の相対キーである。ビューはフェンスの無い素のビューであり、キャッシュは読み取りしかしない。所有権・逆参照・Binding のキャッシュは、それらを実装する ADR で足す。使われなくなったキャッシュの自動的な破棄は作らない。
11. **Lean モデルと DRT。** `spec/Nayutar/WatchCache.lean` に中核と同じ状態機械を書き、`nayutar-drt` の `watchcache` スイートとして実行する。
    - モデルは受け取った変更をすべて持ち続け、何を忘れてよいかを誤りで表す（[[0004]] のストアモデルと同じ書き方）。
    - Go 側は、契約どおりの上流の列と、契約に反する入力を乱数で作り、各ステップの結果を全フィールドについて比べる。
    - [[0017]] の決定 4 に従い、Lean の結果の変異と、わざと誤らせた Go 実装を検出できることを試験に含める。
12. **4 不変条件は、1 本の watch のセッションについての定理として書く。** セッションは、上流の入力、配信の取り出し、ブックマークの要求を任意に並べた列である。
    - **欠落なし**：セッションが配信の取り出しで終わるとき、その watch が受け取るべき変更はすべて配信されている。
    - **重複なし**：配信された変更の列は、受け取るべき変更の列の部分列である（同じ変更を 2 度配信しない。上流に無い変更を配信しない）。
    - **順序保存**：配信された変更のリビジョンは減らない。
    - **ブックマーク単調性**：ブックマークより前に配信された変更とブックマークのリビジョンは、そのブックマーク以下である。後に配信された変更のリビジョンは、そのブックマークより大きい。
    - 主張は `spec/Nayutar/Statements/` に、証明は `spec/Nayutar/Proofs/` に置く（[[0017]]）。主張の配置と `spec/comparator.json` への追加はユーザーが行う。
13. **外殻は試験で確かめる。** インメモリ実装と 3 メンバーの etcd（ビルドタグ `etcd`）の両方で、watch list、ブックマーク、一貫読み取りの待ち合わせとフォールバック、範囲外の拒否、追い越された watch の終了、上流の watch が終わったあとの読み直し、コンパクションの境界を確かめる。
    - 上流の watch の終了は、試験用の上流が `ErrCompacted` と契約に反する変更を注入して起こす。実物のコンパクションが再送中の watch を追い越す場面は、起きるかどうかがタイミングによる（[[0004]]）ので、試験では作らない。
    - ストアへの書き込みとキャッシュ経由の読み取りを並行に流し、porcupine で線形化可能性を検査する（`storetest.RunLinearizability`）。古い状態を現在のものとして返す、わざと誤らせたキャッシュを検査が検出することも確かめる。
    - etcd のリーダーを止めて再選出させるあいだも、キャッシュ経由の線形化可能性検査を流し、そのあとキャッシュが一貫読み取りを返せることを確かめる。過半数喪失と分断をキャッシュの下で注入する試験は作らない。

## 根拠（調査結果・出典）

- **内部不変条件**：[[0004]] の契約は、watch の変更が欠落・重複なくリビジョンの昇順で届くこと、1 トランザクションの変更が連続して届くこと、進捗通知がそのリビジョンまでの配信完了を表すことを定める。変更は 1 件ずつ届くので、リビジョン `r` の変更を 1 件受け取っただけでは `r` が閉じたと言えない。`r` より大きい変更か、`r` 以上の進捗通知を受け取れば、順序の保証から `r` は閉じている。
- **一貫読み取りの線形化可能性**：読み取りは、呼び出しのあとに読んだ `CurrentRev` 以上の閉じたリビジョンの状態を返す。閉じたリビジョンはストアのリビジョンを超えないので、返す状態は呼び出しから応答までのあいだのある時点のストアの状態である。
- **KEP-2340**（ https://github.com/kubernetes/enhancements/blob/master/keps/sig-api-machinery/2340-Consistent-reads-from-cache/README.md 、2026-11-18 確認。ディレクトリ名の `Consistent` は大文字で始まる）：現在のリビジョンを quorum 読み取りで取り、watch キャッシュが追いつくのを待ち、「periodically (every 100ms) request progress until it reaches the requested revision or the request times out」とする。`kep.yaml` は alpha v1.28、beta v1.31、stable v1.34 と記す。KEP は一貫した GET を etcd から返し続けるとするが、本設計は [[0007]] に従い GET もキャッシュから返す。
- **Kubernetes の実装の定数**（ https://github.com/kubernetes/kubernetes/tree/master/staging/src/k8s.io/apiserver/pkg/storage/cacher 、2026-11-18 確認）：
  - `watch_cache_freshness.go`：`blockTimeout = 3 * time.Second`。
  - `progress/watch_progress.go`：`progressRequestPeriod = 100 * time.Millisecond`。
  - `cacher.go`：`defaultBookmarkFrequency = time.Minute`、`DefaultEventFreshDuration = defaultBookmarkFrequency + 15*time.Second`（75 秒）。
  - `watch_cache_history.go`：`defaultLowerBoundCapacity = 100`、`defaultUpperBoundCapacity = 100 * 1024`（102,400）。範囲外は `errors.NewResourceExpired("too old resource version: …")`（410）。
- **フォールバックの扱いは Kubernetes で揺れている**（同 `delegator.go` と https://github.com/kubernetes/kubernetes/blob/master/staging/src/k8s.io/apiserver/pkg/features/kube_features.go 、2026-11-18 確認）：v1.37 で alpha の feature gate `ConsistentListFromCacheSkipTimeoutFallback`（既定は無効）が入り、有効にすると待ち合わせの時間切れで etcd へフォールバックせず、要求を拒否する。本設計は [[0007]] に従いフォールバックする。
- **etcd の版の要件**：KEP-2340 の本文は「v3.4.25+ or v3.5.8+」と書き、Kubernetes のブログ（ https://kubernetes.io/blog/2024/08/15/consistent-read-from-cache-beta/ 、2026-11-18 確認）は「etcd version 3.4.31+ or 3.5.13+」と書く。[[0007]] は両方を記す。本プロジェクトは etcd v3.6 を使う（[[0005]]）ので、どちらの下限も満たす。
- **スナップショット**（同 `store/btree.go`・`store/snapshotter.go`、2026-11-18 確認）：Kubernetes は B-tree の `Clone`（copy-on-write）でイベントごとにスナップショットを取り、リビジョン指定の LIST とページングをそこから返す（KEP-4988。`kep.yaml` は beta v1.34）。import は `k8s.io/utils/third_party/forked/golang/btree` である。
- **B-tree のライブラリ**（GitHub API、2026-11-18 確認）：`google/btree` はアーカイブ済みで、最後の push は 2024-08-21、最新のタグは v1.1.3 である。`tidwall/btree` は 2026-11-02 に push がある。
- **KEP-3157**（ https://github.com/kubernetes/enhancements/blob/master/keps/sig-api-machinery/3157-watch-list/README.md 、2026-11-18 確認）：`sendInitialEvents=true` で現在の状態を合成イベントとして送り、`k8s.io/initial-events-end: "true"` の注釈つきブックマークを送る。ブックマークは「the ResourceVersion (RV) corresponding to the set of objects」を持つ。リビジョンを指定しない要求は一貫読み取りとして扱い、キャッシュが追いつくのを待つ。`kep.yaml` は alpha v1.27、beta v1.32 とし、stable を v1.38 と予定する。v1.38 は 2026-11-18 の時点で未公開である。
- **etcd の watch の保証**（ https://etcd.io/docs/v3.6/learning/api_guarantees/ 、2026-11-18 確認）：Ordered、Unique、Reliable、Atomic（「a list of events is guaranteed to encompass complete revisions」）、Resumable、Bookmarkable（「Progress notification events guarantee that all events up to a revision have been already delivered」）。Atomic は応答 1 つについての保証であり、[[0004]] の `WatchStream` は応答を 1 件ずつに開くので、リビジョンの境界を運ばない。
- **コンパクション**（ https://etcd.io/docs/v3.6/learning/api/ 、2026-11-18 確認）：コンパクション済みのリビジョンから watch を始めると、`compact_revision` が入り、「The watcher will be canceled」となる。

## 検討した代替案

- **ストア契約にリビジョンの境界を足す**：`WatchStream` がリビジョンの終わりを知らせれば、キャッシュは進捗通知を待たずにリビジョンを閉じられ、書いた直後の読み取りが進捗要求 1 往復を待たずに済む。ただし [[0004]] の契約、Lean モデル、2 つの実装、DRT をすべて変える。G1 の計測で待ちが問題になったときに、[[0004]] を補う ADR として起票する。今回は採らない。
- **閉じたリビジョンの変更だけを watch に配信する**：受け手がトランザクションの途中を見なくなる。ただし、静かな接頭辞では変更のたびに進捗要求が要る。etcd の進捗要求は、同じ gRPC ストリームのすべての watch に通知を送るので、キャッシュの数に比例して通知が増える。採らない。
- **`google/btree` か `tidwall/btree` を使う**：前者はアーカイブ済みで修正が来ない。後者は保守されているが、依存が 1 つ増える。必要なのはキー順の写像と安価なスナップショットだけであり、永続 B-tree は小さく、参照実装（ソートした写像）との性質試験で確かめられる。採らない。
- **保持に上限を置かない（[[0007]] の文言どおり）**：更新が集中するとメモリが際限なく伸びる。採らない。
- **キャッシュをストア契約（`store.Store`）の実装にする**：既存の契約テストをそのまま使える。ただし契約は、コンパクションより新しい `fromRev` の watch を必ず受け付ける。キャッシュは保持範囲より古い `fromRev` を拒否する（[[0007]] の決定 5）ので、契約を満たせない。採らない。
- **キャッシュが保持する最古のリビジョンを境界にする**：[[0007]] の決定 5 の最初の文言であり、最初はこのとおりに実装した。差分レビューで、変更が 10,000 件に満たないキャッシュは初期状態を読んだときのリビジョンを保持し続け、そのキャッシュが 1 つあるだけでコンパクションが止まることが分かった（既定の設定で、2 つのキャッシュの片方にだけ 2,000 件書いて再現した）。採らない。[[0007]] の決定 5 は、受け取り終えたリビジョンを境界にする形に書き換えた。
- **初期状態を読み終えていないキャッシュもコンパクションを止める**：読み込み中のキャッシュを守れる。ただし、読み込みに失敗し続けるキャッシュが 1 つあると、コンパクションが止まり続ける。採らない。
- **watch ごとに待ち行列を持つ**：Kubernetes の方式である。遅い受け手の待ち行列がメモリを使う。各 watch がリングバッファ上の位置だけを持てば、遅い受け手は保持範囲に追い越されて終わるだけで、追加のメモリを使わない。採らない。

## 影響とトレードオフ

- **得るもの**：キャッシュの意味論が、ゴルーチンを持たない状態機械に集まり、Lean モデルと 1 ステップずつ比べられる。スナップショットが安価で、リビジョン指定の読み取りとページングをキャッシュから返せる。
- **失うもの**：
  - 書いた直後の一貫読み取りは、その接頭辞に次の変更が来ないかぎり、進捗通知を待つ。進捗要求は 100 ミリ秒に 1 回までなので、直前に要求を送っていれば、待ちは最大で 100 ミリ秒と 1 往復になる。
  - 保持範囲より古いリビジョンを指定した読み取りはストアに渡すが、そのリビジョンがコンパクション済みなら `store.ErrCompacted` になる。
  - watch の受け手は、トランザクションの途中を見ることがある。
  - 自作の B-tree を保守する。
- **引き受けるリスク**：
  - 複数の API サーバを置くと、コンパクションの境界が API サーバごとに違う。本 ADR はこれを解かない。
  - 102,400 件の上限に当たると、履歴が 150 秒を割り、`ErrTooOld` が増える。
  - 進捗要求の頻度が etcd の負荷になる恐れがある。
  - 変更 1 件ごとに、木の根から葉までのノードを複製する。閉じたリビジョンごとのスナップショットがそのノードを保持するので、保持する件数に比例してメモリを使う。ノードの次数（現在は最小次数 16）と値の持ち方は G1 で測って決める。
- **まだ実装しないもの**：過半数喪失と分断をキャッシュの下で注入する試験、HTTP の配信と 410 への対応づけ、封筒の解釈、認可と `Ref` のフィルタ、所有権・逆参照・Binding のキャッシュ、キャッシュの自動的な破棄、複数 API サーバにまたがるコンパクションの境界、フォールバック率や待ち時間の計測値の公開。
- **今後の検証ゲート**：G0 の条件 4（[[0018]]）は、決定 12 の 4 定理を `lake comparator` が保護した状態で満たす。G1 で、watch の遅延、フォールバック率、`ErrTooOld` の率を測り、保持量の初期値と決定 3 の方式（代替案の 1 つめを含む）を見直す。
