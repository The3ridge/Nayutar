# 0015: すべての外部作用をシミュレーション用インターフェース経由とし、gosim 評価後にシミュレータを選ぶ

## コンテキスト

[[0003]] で Go 実装自体を形式証明しない方針を採ったため、分散合意・watch 配信・ノード心拍・スケジューラの並行交錯におけるバグを、再現可能な形で機械的に見つける手段が不可欠になる。実ネットワークや実時計に直接依存したコードは実行ごとに結果が揺らぎ、AI エージェントが失敗原因を切り分けて回帰テストに固定することができない。

一方で、Go 向けの系全体決定論的シミュレータ `gosim` は実験的段階にあり、[[0002]] で定めた Go 1.27.3 以上および最新 2 メジャー版への追従方針と両立するかが未検証である。したがって、I/O 境界の分離だけを先に全コンポーネントへ義務づけ、シミュレータ本体の選定は評価後に切り離して決める必要がある。

## 決定

1. **すべてのコンポーネントは `Clock`・`Net`・`Disk`・`Rand` の 4 つのインターフェースを経由してのみ外界と接する。** 時刻取得、ネットワーク通信、ディスク I/O、乱数生成を直接標準ライブラリから呼ばない。
2. **単体テストは `testing/synctest` と偽ネットワーク実装で行う。** `net.Pipe` 等のインメモリ実装を用い、実ネットワークや実ファイル I/O に依存させない。
3. **系全体のシミュレーションは、単一の乱数シードで全挙動が決まる決定論的イベントキュー上で実行する。**
4. **系全体シミュレータを自作するか `gosim` を採用するかは、G0 の評価を経て後続の ADR で決定する。** 評価基準は、(a) Go 1.27.3 以上で動作すること、(b) 同一シードの 100 回実行でトレースのハッシュがすべて一致すること、(c) Go のサポートリリース（最新 2 メジャー版）への追従コストが許容範囲内であること、の 3 点とする（100 回および評価時期「G0 第 2〜3 週」は初期値とする）。
5. **シミュレーションで失敗したシードは、回帰テストとしてリポジトリに固定する。**

## 根拠（調査結果・出典）

- **`testing/synctest` の仕様と限界**：Go 1.24 で `GOEXPERIMENT=synctest` として実験導入され、Go 1.25 で一般提供になったことを確認した（`https://go.dev/doc/go1.25`）。公式解説（`https://go.dev/blog/synctest`）によれば、バブル内の全ゴルーチンが durably blocked になると偽時計が進むが、「Real network and file I/O do not durably block」であるため、`net.Pipe` などのインメモリ偽実装が別途必須になる。また単一プロセス内の単体・結合試験向けであり、複数ノード・分断・時計ずれを含む系全体の単一シード再現にはイベントキュー基盤が要る。
- **`gosim` の現状**：`https://github.com/jellevandenhooff/gosim` は、決定論的なゴルーチン・スケジューリング、模擬時刻、模擬 TCP ネットワーク・ファイルシステムにより複数マシン分の Go コードを単一プロセスで動かせるが、experimental と明記されていることを確認した。またランタイムフックが Go バージョン別（Go 1.23〜1.26 用を確認）であり、Go 1.27 での動作は未確認である。このため評価なしの先行採用は避ける。
- **決定論的シミュレーションの先行事例と線形化可能性**：FoundationDB（`https://apple.github.io/foundationdb/testing.html`）、TigerBeetle VOPR（`https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md`）、Antithesis（`https://antithesis.com/docs/`）が同型の先例として存在する（所在のみ確認しており、各資料の詳細精読は G0 で行うため現時点では未確認である）。線形化可能性検査の候補には `porcupine` v1.3.1（Go、`https://github.com/anishathalye/porcupine`）がある。
- **数値の位置づけ**：同一シード 100 回の一致、G0 第 2〜3 週での `gosim` 評価、マージ後 200 シード・夜間 10,000 シード・G1 10,000 シード、および決定性未達 6 週での撤退基準は、本 ADR が置く初期値とする。

## 検討した代替案

- **評価なしに最初から `gosim` を全面採用する**：ゴルーチン交錯まで含む決定論性を即座に得られる可能性がある。しかし Go 1.27 対応が未確認で、将来の Go リリースごとにランタイムフックの追従が詰まる恐れがあり、[[0002]] の追従方針と衝突するため採らない。
- **`testing/synctest` のみで系全体も検証する**：標準ライブラリだけで完結し追加基盤が不要になる。しかし実 I/O が durably block しない制約に加え、複数ノード間の分断・遅延・時計ずれを単一シードで再現するイベントキューを欠くため採らない。
- **決定論的シミュレータを作らず、実クラスタの障害注入のみで検証する**：実環境に近い挙動を測れる。しかし再現性が低く失敗シードを回帰固定できないため、[[0003]] が前提とする機械的検証ループに乗らず採らない。
- **Rust 製シミュレータ（`turmoil` や `madsim`）を前提に組む**：`turmoil` 0.7.2（`https://crates.io/crates/turmoil`）は活発に保守されている（`madsim` 0.2.34 は 2025-10-10 以降動きが少ない）。しかしコアを Go で実装する [[0002]] と整合せず、Go バイナリ群の決定論的制御に言語境界を跨ぐ余分な仕掛けが要るため採らない。

## 影響とトレードオフ

- **得るもの**：シミュレータの採否を決め切る前でも、全コンポーネントが `Clock`・`Net`・`Disk`・`Rand` の背後に隔離されるため、単体の `testing/synctest` 試験と後の系全体シミュレーションの両方を書き直しなしで進められる。
- **失うもの**：Go 標準の `time`・`net`・`os`・`math/rand` を直接呼ぶ簡便さが失われ、すべての境界コードにコンテキストや依存注入を通す手間が増える。
- **引き受けるリスク**：外部ライブラリ内部の暗黙な時計・乱数・ソケット利用がインターフェースを素通りし、決定性が壊れるリスクを引き受ける。また `gosim` 不採用時は自作イベントキューの保守コストを負う。
- **今後の検証ゲート**：G0 で `gosim` を上記 3 基準で評価して後続 ADR を起票し、同一シード 100 回実行でのトレースハッシュ一致を確認する（いずれも初期値）。G0 開始後 6 週（初期値）で系全体の決定性が得られない場合は、単体試験を `testing/synctest` に委ね、系全体は `porcupine` 等の履歴検査中心へ切り替える。
