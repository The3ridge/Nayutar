# 0016: 既定拒否のネットワークポリシーはまず nftables で強制し、G2 で eBPF と比較する

## コンテキスト

Nayutar は [[0006]] のとおりテナントを最上位キーかつ隔離単位としており、許可されていないテナント越境通信を既定で遮断するネットワーク隔離が不可欠である。隔離単位をテナントに置く以上、API 面だけでなく実行面でも既定拒否（default-deny）を前提にする必要がある。

一方で [[0001]] は既存のデータプレーン資産を活かす前提（前提 4）と、段階ごとに検証ゲートを設けて設計判断を確定する前提（前提 7）を置いている。パケットフィルタ基盤には `nftables` と eBPF（`cilium/ebpf` による TC / cgroup フック）があるが、初期段階から eBPF や外部制御面に踏み込むと、カーネル・BTF 依存や検証範囲が膨らむ。まず単純で確実な機構で既定拒否を成立させ、大規模検証の段階で eBPF と実測比較する段取りが必要である。

## 決定

1. G1 までの既定拒否ネットワークポリシーは `nftables` で強制する。
2. `nftables` では `policy drop` を設定できるベースチェイン（フックに接続されたチェイン）に `policy drop` を置き、そこから許可ルールを保持するテナントごとの通常チェインへ `jump` する構造を採る（`docs/research/draft_20261117_001.md` §5.5 の「テナント単位の chain で既定 drop」はこの形に改める）。
3. Cilium の非 Kubernetes 経路は詳細が未確認であるため依存しない。
4. G2 で `cilium/ebpf`（TC / cgroup フック）との比較評価を行い、後続の ADR でデータプレーンを最終決定する。

以下の `nftables` 設定は上記構造を示すための例示であり、一致条件の詳細は実装時に定める。

```nft
table inet nayutar {
  chain forward {
    type filter hook forward priority 0; policy drop;
    ip saddr 10.10.0.0/16 jump tenant_a
  }
  chain tenant_a {
    ip daddr 10.10.0.0/16 accept
  }
}
```

## 根拠（調査結果・出典）

- 内部前提との整合：[[0001]] の前提 4・7 に従い、Linux カーネル標準の `nftables` でまず最小構成の既定拒否を実装し、G2 で性能と運用性を比較した上で後続を判断する（`docs/research/draft_20261117_001.md` §5.5・§9）。これにより [[0006]] が定めるテナント境界をデータプレーンでも担保する。
- `nftables` のチェイン仕様：`nftables` では `policy`（`accept` / `drop`）はフックに接続されたベースチェインにのみ設定でき、既定値は `accept` であること、テーブルおよび通常チェインには `policy` が存在しないことを一次資料で確認した（https://wiki.nftables.org/ ）。そのためテナントごとの通常チェイン自体には `policy drop` を置けず、ベースチェインの `policy drop` と通常チェインでの明示許可・`jump` を組み合わせる必要がある。
- eBPF との比較材料：`cilium/ebpf` の最新リリースが v0.22.0 であることを一次資料で確認した（https://pkg.go.dev/github.com/cilium/ebpf?tab=versions ）。ただし BTF 等の環境依存や検証コストのリスク（`docs/research/draft_20261117_001.md` §9）があり、Cilium の非 Kubernetes 経路も未確認である。

## 検討した代替案

- **最初から eBPF（`cilium/ebpf`）だけで実装する**：TC / cgroup フックにより高スループットやソケット層の制御を狙える。しかし G1 の段階から BTF やカーネル版依存の検証負担を負うことになり、比較基準もないため採らない。
- **Cilium をそのままポリシーエンジンとして組み込む**：L3/L4/L7 にわたる既存の機能群を利用できる。しかし Cilium の非 Kubernetes 経路が未確認であり、Kubernetes 前提の制御面や運用複雑性を取り込む恐れがあるため採らない。
- **`iptables` を使う**：既存の事例やツールが多い。しかし規則集合をまとめて差し替える操作やテナントごとのチェイン構成は `nftables` のほうが表しやすく、あえて `iptables` を選ぶ理由がないため採らない（両者の性能比較は未確認である）。
- **G2 までポリシーを実装せず既定許可で進める**：G1 のデータプレーン実装が軽くなる。しかしテナント隔離を中核とする設計に反し、越境通信の否定試験を早期に回せないため採らない。

## 影響とトレードオフ

- **得るもの**：外部の重いデータプレーン制御面に依存せず、G1 の時点からテナント間の既定拒否を検証可能な形で強制できる。G2 で eBPF と公平に比較するための基準線も確保できる。
- **失うもの**：cgroup フック等によるソケット層での最適化や、大規模ルール集合における eBPF 特有の高速化は G2 の比較完了まで得られない。
- **引き受けるリスク**：テナント数とエンドポイント数の増加により、`nftables` のルール更新時間やパケット処理遅延が G1 後半〜G2 でボトルネックになる可能性がある。また G2 で eBPF へ切り替える場合、ポリシー適用部の書き換えコストが発生する。
- **今後の検証ゲート**：G1（`docs/research/draft_20261117_001.md` §8.2）でテナント越境通信が既定で拒否される否定試験を通し、G2（同 §8.3）で `nftables` と `cilium/ebpf` v0.22.0（TC / cgroup フック）の性能・更新遅延・保守負荷を比較する。G1 の段階で `nftables` の規模・性能が要件を満たさない場合、または G2 の比較結果が eBPF 移行を裏付けた場合に、後続 ADR で切り替える。
