# 0013: 葉パス所有権を独立キーに分離し本体と同一トランザクションの CAS で更新する

## コンテキスト

[[0001]] の前提 2 に従い、Nayutar は所有権と apply の中核に kisage の葉パス所有権モデル（共有所有状態 σ：葉パスから Actor、Origin、revision への写像）を採る。[[0004]] と [[0006]] により、オブジェクト本体は `/t/<tenant>/o/<group>/<kind>/<name>`、所有権は `/t/<tenant>/own/<group>/<kind>/<name>` に置き、ストア契約は `mod_revision` の比較（CAS）付き `Txn` を備える etcd v3 API サブセットとした。

既存の kisage はローカルファイル向けであり、`provider/lock.go` が共有ストアから Resource の順に `flock(2)` を 2 つ取る排他区間内で、`intent` → `providerApply` → `validate` → `stabilize` → `commit`（および `recover`）の多段階手順を実行する（kisage の ADR 0004）。API サーバでは多テナントの並行書き込みを単一の原子的 `Txn` へ写像し直す必要があり、同時に所有権メタデータの肥大化と書き込み遅延の増加を抑えなければならない。

また、kisage の Lean 実装と文書（`Kisage/Theorems.lean`、`Kisage/Protocol.lean`、kisage の ADR 0004）を確認したところ、CAS 前提への移行は既存の Plan 定理 11 個とプロトコル不変条件 9 個をそのまま再証明するだけでは済まず、単一パス射影と多段階ロックを前提としたプロトコルモデル自体の再構築を伴う G0 最重の検証課題であることが分かった。

## 決定

1. 葉パス所有権 σ（葉パスから Actor、Origin、revision への写像）はオブジェクト本体に含めず、独立キー `/t/<tenant>/own/<group>/<kind>/<name>` に格納する。
2. オブジェクト本体と所有権記録は、両キーの `mod_revision` に対する CAS を比較条件とする単一のストア `Txn` で原子的に更新する。比較失敗は競合として呼び出し元へ返し、暗黙の再試行は行わない。
3. 所有権競合・構造衝突・外部ドリフトは kisage の診断コード（`K101`–`K604`）を返して fail-closed で停止し、`force` による強制上書きは設けない。
4. `apply` と `prune` は別操作に分離し、`prune` は `Origin = Created` の葉のみを削除対象とする。
5. kisage の `--expect` と `--owner-revision` を書き込み API の前提条件パラメータとして引き継ぐ。
6. 所有権メタデータを抑えるため、作成者を既定の所有者として異なる所有者の葉のみを記録し、trie と整数符号化した Actor 辞書で保持する。部分木所有（`spec/container/app/**`）は葉集合の略記として定義し、定理の主張を変えない。ゲート閾値は所有権サイズを本体の 20% 以下、書き込み p99 増分を +2 ms 以内とし、いずれも初期値とする。
7. ファイル版 kisage（ファイルロック・Intent ステージング・回復）はローカル用途向けにそのまま維持し、API サーバ版は既存 kisage のインプレース改変ではなく新しいプロトコルモデルとして構築する。

## 根拠（調査結果・出典）

- **kisage の検証到達点（kisage の `README.md`、`docs/verification-status.md`）**：kisage（`https://github.com/Kaikei-e/kisage`）v0.1.2（2026-10-30、Apache-2.0、Go 1.27.3、Lean v4.35.0）では、`Kisage/Theorems.lean` が純粋関数 `Plan` の安全性 11 性質（19 定理）を `sorry` なしで証明し、`kisage-drt` が 1,728 ケースを Go 実装と比較していることを確認した。`Plan` の 11 性質は純粋計画関数に関するものであり CAS 版でも引き継げる見込みだが、現時点では期待にとどまり未確認である。
- **プロトコルモデル再構築の必要性（kisage の `Kisage/Protocol.lean`、kisage の ADR 0004）**：`ProtocolState.storeEntry : Option OwnerEntry` は他 Actor の予約を入力として受け取る単一パス射影であり、複数パス・複数テナントのストア全体はモデル化されていないことを確認した。`ProtocolInvariant` の 9 項目は原子保存・条件付き適用・2 段の排他ロックを信頼境界に置いて多段階遷移を保証するものである。単一 CAS `Txn` へ移すと Intent 永続化・適用後契約検証・`stabilize`・`recover` が縮退または消滅するため、行単位の再証明ではなくプロトコルモデルの書き直しが必要となる。
- **ESR と kisage 側の段階（kisage の `docs/verification-status.md`、kisage の ADR 0005）**：kisage でも ESR 本体は未証明であり、単一パス上の有限収束と候補ランク関数のみが形式化されていることを確認した（ESR 本体は kisage の ADR 0005 Phase 5）。また kisage の ADR 0001〜0005 は全件 `proposed` であり、同文書自身もテスト通過を Phase 0–2 の完了とみなさないと明記していることを確認した。
- **独立キーと単一 CAS `Txn`**：etcd v3 の `Txn` は同一トランザクション内で複数キーの `mod_revision` を比較できることを公式仕様（https://etcd.io/docs/v3.5/learning/api/ ）で確認した。所有権を `/t/<tenant>/own/...` へ分離することで、本体読み取りと watch 配信から所有権メタデータを切り離しつつ、本体・所有権・[[0010]] の逆参照索引の整合性を 1 回の `Txn` で維持できる。
- **保守的削除と信頼境界（kisage の `docs/PRINCIPLE.md`、`README.md`）**：`theorem3_conservative_deletion` は `prune` モード・宣言外・`Origin = Created`・`Pending` なし・観測値＝`LastApplied`・`Delete+Own` 権限を満たす葉だけを削除対象とする。kisage の `docs/PRINCIPLE.md` が記すとおり、値の一致だけを比べる判定は、外部での削除と同じ値での再作成（ABA）を検知できない。API サーバ版では `mod_revision` の CAS で更新間の割り込みを検知できる見込みだが、これは CAS 版モデルで確かめる。なお kisage は Actor と Scope を保護されたホスト設定からだけ読み、自己申告の Actor を無視する。

## 検討した代替案

- **オブジェクト内部に `managedFields` を埋め込む（Kubernetes SSA / KEP-555 方式）**：https://kubernetes.io/docs/reference/using-api/server-side-apply/ が採る方式であり、1 キーで完結し `force` による強行も定義できる。しかし本体オブジェクトと watch ペイロードが所有権メタデータで肥大化し、本体を変えずに所有権の表現（trie や辞書圧縮）を最適化する余地もなくなるため採らない。
- **kisage のファイルロックプロトコルを残し、ストア前にロックサービスを置く**：既存の `Kisage/Protocol.lean` を流用しやすい。しかし分散ロックの単一障害点とリース失効処理を持ち込むことになり、[[0004]] で Lease をストア契約から外した方針に反するため採らない。
- **本体と所有権を 2 つの独立した `Txn` に分け、回復処理で整合させる**：1 `Txn` あたりのキー数は減る。しかし中間のクラッシュや並行更新に備えた Intent ステージング・回復・不整合診断が再び必要となり、単一 `Txn` が持つ原子性を手放すことになるため採らない。
- **葉パス単位ではなくフィールドグループ単位の所有権にする**：状態空間とメタデータ量は小さくなる。しかし細粒度の競合回避と未宣言部分の保護という [[0001]] の要件を弱めるため初期方式にはせず、G0 の kill criterion に該当した際の撤退先とする。
- **所有権を持たない Last-Writer-Wins にする**：実装は最も単純になる。しかし複数コントローラや利用者による部分上書きと意図しない削除を防げず、[[0001]] が中核に据えた葉パス所有権モデルそのものを放棄することになるため採らない。

## 影響とトレードオフ

- **得るもの**：本体と所有権の分離により本体側の読み取り・watch 負荷を軽く保ちつつ、単一 CAS `Txn` によって不完全適用やファイル回復手順を排除できる。`force` 禁止と `apply`/`prune` 分離により意図しない上書きと誤削除を防げる。
- **失うもの**：1 回の更新 `Txn` で本体・所有権・[[0010]] の逆参照索引を同時に扱うため、キー数増に伴うストア遅延増と、`force` 不在による明示解消（`adopt`/`release`）の運用手間が増える。またファイル版 kisage とは別のプロトコルモデルを保守する負担が生じる。
- **引き受けるリスク**：CAS 版の複数パス・複数テナント所有権プロトコルの形式証明は G0 で最も重い課題であり、証明の作業規模は未確認である。所有権サイズ 20% 以下・書き込み p99 増分 +2 ms 以内を達成できるかも実装前は未確認である。
- **今後の検証ゲート**：
  - G0：[[0002]] の `spec/` に CAS 版プロトコルモデルを構築し、Plan 安全性 11 性質と新プロトコル不変条件の証明（`sorry` ゼロ）、および [[0003]] の Lean–Go DRT 1,000 ケース（初期値とする）を通す。CI で `sorry` 数を追跡し、3 か月（初期値とする）以内に CAS 版の所有権定理を証明できなければフィールドグループ単位へ粗粒化する（kill criterion）。
  - G1：所有権サイズを本体の 20% 以下、書き込み p99 増分を +2 ms 以内（いずれも初期値とする）に収めることを実測で検証する。
