# 0019: 単一 etcd クラスタを、3 メンバーの試験クラスタ・Compact を持たないテナントビュー・相乗り計測で実現する

## コンテキスト

[[0005]] は、G0〜G1 の強整合ストアを 3 台構成の単一 etcd v3.6 クラスタとし、全テナントのデータを `/t/<tenant>/` の下に置き、G0 ではホット領域も同じクラスタに載せる、と決めた。しかしコードはこの構成をまだ表していない。

- etcd を相手にする試験（契約テスト・線形化可能性検査・DRT）は、メンバー 1 台のクラスタにしかかけていない。複数メンバーで初めて現れる挙動（フォロワーの適用遅れ、リーダー交代、エンドポイントの切り替え）は試験の外にある。
- テナントを接頭辞に閉じ込めるコードが無い。`storetest.Scope` は試験用で、リビジョンをずらす。
- `Compact` と `CurrentRev` はクラスタ全体で 1 つである。テナントごとの見え方をどうするかは [[0005]] も [[0006]] も決めていない。
- ホット領域を同じクラスタに載せたときの影響を測る手段が無い。[[0005]] は、高頻度イベントが合意遅延を押し上げる可能性をリスクに挙げている。
- 開発環境の宣言 `config/dev.lkal` は空である。

[[0006]] は `proposed` である。本 ADR が使うのは `/t/<tenant>/` という接頭辞だけであり、その下の配置（`o/`・`own/`・`ref/`・`bind/`）と `/sys/`・`/x/` は [[0006]] の範囲に残す。

## 決定

1. **試験の既定を 3 メンバーにする。** `etcdtest.Start` は、ループバック上に 3 メンバーの etcd を静的ブートストラップで起動する。クライアントには 3 つのエンドポイントをすべて渡す。契約テスト・線形化可能性検査・DRT はすべてこのクラスタにかけ、メンバー 1 台の構成は残さない。試験は 3 メンバーすべてが 3.6 系を報告することを確かめる。試験用のメンバーは `--unsafe-no-fsync` で起動する。
2. **メンバー障害を注入する。** 線形化可能性検査の最中に、メンバーを 1 台ずつ停止して再起動する。対象にはリーダーを含める。同時に止めるのは 1 台までで、過半数は常に残す。
   - エラーで返った `Txn` は結果不明として扱う。履歴には、最後まで戻らなかった操作として記録し、適用された場合と適用されなかった場合の両方を許す。
   - エラーで返った読み取りは状態を変えないので、履歴に入れない。
   - watch は障害で終わってよい。試験は、最後に受け取ったリビジョンの次から開き直し、つなげた列に欠落・重複・順序の入れ替わりが無いことを確かめる。
   - 2 台同時の停止（過半数の喪失）、ネットワーク分断、ディスク障害は注入しない。
3. **テナントビューを置く。** `core/store/tenant` は、`store.Store` を `/t/<tenant>/` の下に閉じ込めるビューを提供する。
   - テナント名は RFC 1123 のラベルとする。小文字の英数字と `-` だけを使い、先頭と末尾は英数字、長さは 1〜63 バイトである。これ以外の名前ではビューを作れない。
   - ビューの型は `Get`・`Range`・`Txn`・`Watch`・`CurrentRev` だけを持つ。`Compact` は持たない。コンパクションはクラスタ全体の `store.Store` を持つ側だけが行う。
   - ビューはキーの接頭辞だけを付け外しする。リビジョンは変えない。したがってテナントが見るリビジョンはクラスタ全体のリビジョンであり、他テナントの書き込みでも進む。
   - ビューは権限の境界ではない。クラスタ全体の `store.Store` を持つコードは、どのテナントのキーにも届く。etcd の認証と RBAC は本 ADR では設定しない。
4. **ホット領域に専用の型を作らない。** G0 のホット領域は同じ `store.Store` を使う。専用のインタフェースやキー接頭辞は、G1 で別層への分離を検証するときに入れる。代わりに、相乗りの影響を測る計測を `storetest` に置く。計測は、強整合側の書き込みと watch の遅延を、ホット側の高頻度書き込みが無いときと有るときで比べ、分位点を報告する。合否の閾値は置かない。
5. **開発用クラスタを宣言する。** `config/dev.lkal` に、etcd の版と 3 メンバーの URL を宣言する。`cmd/dev-etcd` はその宣言を `lkal json -plain` で読み、宣言と同じ版の etcd を 3 メンバーでローカルに起動する。版が宣言と違えば起動しない。データの既定の置き場所はリポジトリの外にする。
6. **アダプタは、etcd がメンバー自身の状態だけで答える経路を定足数読み取りに通す。** 3 メンバーにしたことで、`etcdstore` が契約を破る経路が 3 つ見つかった。どれも、遅れているフォロワーが応答したときにだけ現れる。
   - 書き込みを持たない `Txn`（比較だけの `Txn`）には、線形化可能な読み取りを 1 つ、成功側と失敗側の両方に添える。
   - `fromRev` が 0 の `Watch` は、先に `CurrentRev` を読む。etcd の watch は開始リビジョン 0 のまま開き、読んだリビジョン以下の変更はアダプタが捨てる。
   - `fromRev` が正の `Watch` は、先にそのリビジョンを線形化可能に読む。コンパクション済みなら、`ErrCompacted` で終わった watch を返す。未来のリビジョンは許す。
   - `Watch` の中の読み取りが呼び出し側のコンテキストの終了で失敗したときは、エラーを返さず、そのコンテキストの誤りで終わった watch を返す。
   - 回帰テストは、フォロワーのプロセスを一時停止して遅らせ、そのフォロワーだけに接続したクライアントで問い合わせる。

## 根拠（調査結果・出典）

- **内部不変条件（[[0004]] の契約）**：`core/store/store.go` は、`atRev` が 0 の読み取り・`CurrentRev`・`Txn` を線形化可能と定める。`RequestProgress` は watch が追いつくまで要求を黙って捨ててよく、呼び出し側は十分なリビジョンの通知が届くまで再要求する。watch は、ストアの誤りで終わったとき `Err` でその誤りを返す。3 メンバーでも契約の文面は変えずに検査できる。
- **3 メンバーの静的ブートストラップ**（ https://etcd.io/docs/v3.6/op-guide/clustering/ ）：各メンバーに `--name`、`--initial-advertise-peer-urls`、`--listen-peer-urls`、`--listen-client-urls`、`--advertise-client-urls`、`--initial-cluster-token`、`--initial-cluster`、`--initial-cluster-state new` を渡す。`--initial-cluster` と `--initial-cluster-token` は全メンバーで同じ値にする。同じ設定で複数の試験クラスタを作るときは、クラスタごとに別のトークンを与える。
- **メンバー障害時の挙動**（ https://etcd.io/docs/v3.6/op-guide/failures/ ）：3 メンバーのクラスタは 1 台の停止に耐える。リーダーが止まると、選挙タイムアウト程度のあいだ書き込みは処理されず、その間の書き込みは待たされるかタイムアウトする。旧リーダーに送られて未コミットの書き込みは失われることがあるが、コミット済みの書き込みは失われない（"no committed writes are ever lost"）。過半数を失うと書き込みを受け付けなくなる。
- **API の保証**（ https://etcd.io/docs/v3.6/learning/api_guarantees/ ）：KV 操作は耐久性と厳密な直列化可能性を持つ。タイムアウトやネットワーク障害のとき、クライアントは操作が完了したか分からないことがある。リーダー選挙のあいだ etcd は操作を中断することがあるが、未応答の要求に中断の応答は送らない。watch は順序どおり・重複なし・欠落なしで、最後に受け取ったリビジョンから再開できる。
- **結果不明の操作の扱い**（ https://github.com/jepsen-io/jepsen/blob/main/doc/tutorial/03-client.md ）：Jepsen は、起きなかったと分かる操作を `:fail`、分からない操作を `:info` とし、後者を「起きたかもしれないし起きなかったかもしれない」ものとして検査する。porcupine の `Operation` は呼び出しと応答の時刻で閉区間を表すだけで、結果不明の操作を表す専用の手段は無い（ https://pkg.go.dev/github.com/anishathalye/porcupine ）。そこで応答の時刻を履歴の末尾に置く。その操作はそれ以降のすべての操作と並行になり、検査器は最後に並べることもできるので、適用されなかった場合も説明できる。
- **テナント名**（ https://www.rfc-editor.org/rfc/rfc1123.txt §2.1、 https://kubernetes.io/docs/concepts/overview/working-with-objects/namespaces/ 、 https://kubernetes.io/docs/concepts/overview/working-with-objects/names/ ）：RFC 1123 は、RFC 952 のホスト名の構文から先頭文字の制限を緩めて英字または数字とし、63 文字までの名前を扱うことを必須とする。Kubernetes は namespace 名に RFC 1123 の DNS ラベルを要求する。Kubernetes の現行の検証は先頭を英字に限るので、Kubernetes の namespace 名はすべて本 ADR のテナント名として通る。ラベルは `/` を含まないので、`/t/a/` と `/t/ab/` のように、あるテナントの接頭辞が別のテナントの接頭辞の先頭になることは無い。
- **リビジョンとコンパクションはクラスタ全体のもの**（`core/store/storetest/scope.go`）：既存の試験用ビュー `Scope` は「リビジョンとコンパクションは全体のままなので、ほかに書き込む者がいないことは呼び出し側が保証する」と書いている。etcd の `clientv3/namespace` もキーの接頭辞だけを付け外しする（ https://pkg.go.dev/go.etcd.io/etcd/client/v3/namespace ）。
- **etcd の RBAC**（ https://etcd.io/docs/v3.6/op-guide/authentication/rbac/ ）：ロールにはキー接頭辞（範囲 `[/foo/, /foo0)`）への read・write・readwrite を与えられる。権限の境界を etcd 側に置くことは可能だが、本 ADR では使わない。
- **版**（ https://etcd.io/blog/2026/oct-22-patch-release/ ）：CI とモジュールが固定している v3.6.16 は 2026-10-22 のパッチリリースである。
- **比較だけの `Txn` は定足数読み取りを通らない**（ https://github.com/etcd-io/etcd/blob/v3.6.16/server/etcdserver/v3_server.go 、 https://github.com/etcd-io/etcd/blob/v3.6.16/server/etcdserver/txn/txn.go ）：`EtcdServer.Txn` は、読み取り専用の `Txn` を `IsTxnSerializable` が偽のときだけ `linearizableReadNotify` に通す。`IsTxnSerializable` は成功側と失敗側の操作をすべて調べるので、どちらも空なら真を返す。その `Txn` は応答したメンバーの状態だけで評価される。3 メンバーに対する DRT が、書き込みの直後に 2 つ古いリビジョンを返す例を 1,000 ケース中 1 件で検出した。フォロワーを一時停止する回帰テストは、修正前は 3 回中 3 回失敗し（200 リビジョン古い応答）、修正後は 10 回中 10 回通った。
- **開始リビジョン 0 の watch はメンバー自身のリビジョンから始まる**（ https://github.com/etcd-io/etcd/blob/v3.6.16/server/storage/mvcc/watchable_store.go ）：`watchableStore.watch` は、`startRev` が 0 のとき `minRev` を `s.store.currentRev + 1` にする。これは応答したメンバーのリビジョンである。契約は、`fromRev` が 0 の watch を「呼び出しのあとの最初の変更から」と定める。3 メンバーに対する DRT が、直前に確定した変更を配信する例を、1,000 ケースの実行 4 回のうち 1 回で検出した。回帰テストは、修正前は 3 回中 3 回失敗し、修正後は 10 回中 10 回通った。
- **未来の開始リビジョンを持つ watch に etcd は進捗を返さない**（同じ `watchable_store.go` の `progressIfSync`）：ストアのリビジョンが watch の `startRev` より小さいあいだ、進捗要求は答えられない。最初に試した修正は、読んだリビジョンの次から etcd の watch を開くものだった。これは書き込みの無いストアで進捗要求が永久に答えられず、DRT が全シードで時間切れになった。契約は、`fromRev` が 0 の watch には届くべき開始リビジョンが無いので、進捗要求に答えることを求める。そのため開始リビジョンは 0 のままにし、古い変更を捨てる方式にした。
- **コンパクション済みのリビジョンからの watch も、メンバー自身の状態で判定される**（同じ `watchable_store.go` の `watch`）：開始リビジョンがメンバーの現在のリビジョンより大きい watch は、同期済みとして登録され、コンパクションとの照合を受けない。差分レビューがこの経路を指摘した。フォロワーを一時停止し、残りの 2 メンバーに 50 回書いてからコンパクションし、そのフォロワーに最初のリビジョンからの watch を開くと、修正前は 8 回中 7 回、`ErrCompacted` で終わらずに 50 件を配信した。契約は、コンパクションより前の正の `fromRev` は必ず `ErrCompacted` で終わると定める。
- **`Watch` の中の読み取りと期限**（`core/store/storetest/contract.go` の `testEndedWatchReportsItsError`）：契約テストは、期限 1 ms のコンテキストで `Watch` を 50 回呼び、`Watch` が watch を返したうえで、その watch が期限の誤りで終わることを求める。読み取りを足した直後の版は、読み取りが期限に間に合わないと `Watch` 自体がエラーを返し、このテストに落ちた。
- **障害注入中の watch は、実測では終わらなかった**：`TestWatchAcrossMemberFailures` を 3 回実行し、どの回も watch は一度も終わらず、開き直しは 0 回だった（確認済みの書き込み 173〜174 件をすべて 1 回ずつ配信、結果不明の書き込みは 1〜2 件）。接続先のメンバーが止まると、clientv3 が別のメンバーへつなぎ直して watch を続けるためである。したがってこの試験は、メンバー障害をまたぐ配信の欠落・重複・順序を確かめているが、開き直しの経路は通していない。
- **相乗り計測の実行例**（2026-11-18、開発機のループバック上、fsync なし、各 2 秒、強整合側 50 件／秒、ホット側 8 並列）：ホット側の書き込みが無いとき、強整合側の `Txn` は p50 1.6 ms・p99 2.5 ms、watch の配信は p50 1.5 ms・p99 2.3 ms だった。ホット側が 2 秒で 25,763 件を書いたとき、`Txn` は p50 0.8 ms・p99 2.8 ms、watch は p50 0.7 ms・p99 2.0 ms だった。この条件では相乗りによる悪化は読み取れなかった。1 回の実行であり、fsync を省いているので、運用時の値の根拠にはならない。

## 検討した代替案

- **メンバー 1 台の試験を残し、3 メンバーの試験を足す**：原因の切り分けはしやすい。しかし [[0005]] が運用するのは 3 台構成だけであり、試験の時間とコードがほぼ倍になるため採らない。
- **DRT だけメンバー 1 台のままにする**：件数の多い DRT の時間を抑えられる。しかし Lean モデルとの一致を確かめる対象が、運用する構成と違うものになるため採らない。
- **障害を注入しない**：3 メンバーで起動するだけでは、3 台にする理由である耐障害性を確かめられないため採らない。
- **エラーで返った `Txn` を失敗として履歴から落とす**：適用済みの書き込みを履歴から消すことになり、正しい実装を線形化不能と誤判定するため採らない。
- **ビューも `store.Store` を満たし、`Compact` をそのまま通す**：既存の契約テストをそのままかけられ、`store.Store` を求める箇所にそのまま渡せる。しかし 1 つのテナントの `Compact` が全テナントの履歴を消すため採らない。
- **ビューは `store.Store` を満たすが、`Compact` は常にエラーを返す**：どこにでも渡せる。しかし契約が定める `Compact` の意味から外れた実装を `store.Store` として流通させることになるため採らない。
- **ビューがテナントごとにリビジョンを振り直す**：他テナントの書き込みがリビジョンに現れなくなる。しかし etcd のリビジョンはクラスタに 1 つであり、振り直しには書き込みごとの追加の状態と、[[0004]] の契約に無い意味論が要るため採らない。
- **テナント名を `/` と制御文字以外は自由にする**：柔軟である。しかし大文字小文字や Unicode 正規化の違いで見分けにくい名前を許し、Kubernetes の namespace との写像にも規則が要るため採らない。
- **テナントを不透明な固定長の ID にする**：改名に強い。しかしキーを見ても誰のテナントか分からず、名前との対応表が G0 から要るため採らない。
- **ホット領域用の `Store` の継ぎ目を先に置く**：G1 での差し替えは楽になる。しかし利用者のまだ居ない抽象になるため採らない。
- **相乗り計測に合否の閾値を置く**：[[0005]] は G0 の閾値を定めていない。試験は `--unsafe-no-fsync` のループバック上で走るので、絶対値は運用時の値を表さない。根拠の無い閾値を新設することになるため採らない。
- **`fromRev` が 0 の watch を、読んだリビジョンの次から開く**：捨てる処理が要らず単純である。しかし etcd は開始リビジョンが未来の watch に進捗を返さないので、契約の `RequestProgress` を満たせないため採らない。
- **`fromRev` が 0 の watch を、読んだリビジョンから開いて重複分を捨てる**：進捗は返る。しかし etcd はその watch を未同期として扱い、同期の周期を待つぶん watch の開始が遅れるため採らない。
- **開発用クラスタを宣言だけにして起動手段を置かない**：宣言と実際のクラスタが一致しているかを確かめる手段が無くなるため採らない。

## 影響とトレードオフ

- **得るもの**：[[0005]] の構成（3 メンバー・テナント接頭辞・相乗り）を、契約テスト・線形化可能性検査・DRT が直接の対象にする。1 台の停止とリーダー交代をまたいで契約が保たれることを機械判定できる。メンバー 1 台では現れなかったアダプタの契約違反 3 件を、運用の前に取り除けた。テナントのコードはクラスタ全体のコンパクションに触れない。
- **失うもの**：メンバー 1 台での切り分けはできなくなる。etcd を使う試験は 3 プロセスを起動するぶん遅くなる。比較だけの `Txn` とすべての `Watch` は、定足数読み取り 1 回のぶん遅くなる。テナントビューは `store.Store` ではないので、`store.Store` を求めるコードにはそのまま渡せない。テナントからは他テナントの活動量がリビジョンの進みとして見える。
- **引き受けるリスク**：障害注入の試験は時間に依存し、不安定になる恐れがある。試験が確かめるのは 1 台停止までであり、分断や過半数喪失の挙動は確かめていない。相乗り計測の数値は fsync を省いたループバック上のもので、G1 の判断にそのまま使えない。[[0006]] が `/t/<tenant>/` 以外の最上位を選べば、ビューの接頭辞を変えることになる。
- **今後の検証ゲート**：G0 で、3 メンバーのクラスタに対する契約テスト・線形化可能性検査（障害注入あり）・DRT 1,000 ケース以上が通ることを確かめる。G1 で、相乗り計測を fsync を有効にした実機に対して行い、[[0005]] の watch p99 1 秒以内と照らす。分断と過半数喪失の注入は、[[0015]] の決定論的シミュレーションを決めるときに扱う。
